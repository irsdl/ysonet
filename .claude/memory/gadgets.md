# Gadgets (ysonet/Generators/)

- 2026-07-29 - `-t` IN YSONET IS A SELF-EXPLOIT, AND THAT IS THE WHOLE POINT, not a side effect to apologise for. It deserializes the FINISHED payload in the ysonet process on the OPERATOR'S OWN MACHINE, so the payload's real effect fires on YOU - that is how you confirm a payload works. It is accepted even for full code execution: `-t` on ObjectDataProvider / TypeConfuseDelegate really launches the `-c` command on your box, and `-t` on the network gadgets really makes your machine resolve/connect out (proven in the OOB run). So "it would run the exploit locally" is NEVER by itself a reason to refuse `-t` - running it locally is what `-t` IS. Teach it as "self-exploitation is the feature", with a short carve-out list, NOT as "we avoid self-exploitation". On the maintainer's call the "run your own code/bytes" cases now ACCEPT `-t`, because running your own payload on yourself IS the self-exploit `-t` promises: `AssemblyInstallerLoad` (loads+runs YOUR DLL's installer ctors here - the same self-run `-t` on ObjectDataProvider does) and `ResXFileRef` on EVERY variant (v2 runs a BinaryFormatter over the `.resources` you named, v3 activates your named type, both in-process) were flipped from refuse to accept. So "operator-supplied and unparsed" is NO LONGER a refusal reason on its own. `TempFileCollection` was ALSO flipped to accept even though `-t` there is genuinely DESTRUCTIVE (it deletes the files you named) - the maintainer's call that a self-exploit deleting your own files is still the point of `-t`; the one safeguard added is that its fidelity guard runs on a `Test=false` probe FIRST, so a `--minify`-rewritten path is refused BEFORE `-t` can delete the wrong file (the probe-first order ResXFileRef/ResourceDictionary use, now required on TempFileCollection too because accepting `-t` made ordering matter). The ONLY refusal left in the whole catalogue is `WbemClassObjectUnmarshal` v2 (YOUR unparsed blob into native `CoUnmarshalInterface`, which can CRASH ysonet unpredictably - a process-kill risk, NOT "run your code"), plus DoS gadgets (routed to a child via IsolatedSelfTest so the child dies, not ysonet). Everything else accepts `-t`. When you review a `-t` refusal, ask "is this running the operator's own payload/effect on themselves?" (accept, even if destructive) vs "can it crash the tool from bytes ysonet never parsed?" (the last carve-out). - I twice mis-taught self-exploit as the thing to avoid; it is the feature, and the whole catalogue was over-restricted (AssemblyInstallerLoad, ResXFileRef v2/v3, TempFileCollection) until this sweep left only the native-crash case refused.

- 2026-07-29 - A `[TypeConverter]` ON A TYPE IS A GADGET REACHABLE FROM EXACTLY TWO SERIALIZERS in this catalogue, and no more, because the sink is "run a TypeConverter over a scalar the serializer has already typed". `ResXFileRef` is the reference case: `System.Resources.ResXFileRef` carries `[TypeConverter(typeof(Converter))]`, and `Converter.ConvertFrom` opens the string's path on the target and (per the type name it also parses) reads the file's text back (`System.String`), runs a BinaryFormatter over it (`System.Resources.ResourceSet`, whose `Stream` ctor is the nested deserializer), or `Activator.CreateInstance(type, stream)`. The two that fire: XAML (an object element's INITIALIZATION TEXT is handed to the type's converter) and YamlDotNet < 5 (a tagged ROOT scalar resolves the type from the tag, then `ScalarNodeDeserializer` falls back to `TypeDescriptor.GetConverter(expectedType).ConvertFrom`). Every other supported serializer is out for one of three structural reasons, and the split is worth keeping because it decides the whole list in one step: (1) NO PARAMETERLESS CTOR AND NO WRITABLE MEMBER - JavaScriptSerializer ("No parameterless constructor"), both SharpSerializer modes (it uses `Convert.ChangeType`, never `TypeDescriptor`), XmlSerializer, the DataContract family and MessagePack typeless all build a contract from read-write members and this type has two arg-taking ctors and three read-only props; (2) THE CONVERTER IS NEVER CONSULTED - BF/Soap/Los/NDCS/FsPickler rebuild the object from its `fileName`/`typeName` FIELDS, producing an inert `ResXFileRef` that reads no file (the dangerous SILENT pass: it round-trips cleanly); (3) NOWHERE TO DECLARE IT - Json.NET builds a string contract but a JSON string at an `object` root carries no `$type`, and with a declared `ResXFileRef` target it throws InvalidCastException because ConvertFrom returns the CONVERTED object, and there is no settable member of `ResXFileRef` anywhere in the .NET 4 framework to name (`ResXDataNode.FileRef` is getter-only), which also kills YamlDotNet-by-member and FastJson. So YamlDotNet is in ONLY via the root-scalar tag, not via a member. The value grammar is `ResXFileRef.ToString()`'s: quote the path when it holds `;` or `"` (the parser reads an unquoted path to the FIRST `;`, a quoted one to the LAST `"`), then `;typeName`, then `;encoding`. Reuse the composition in a fidelity guard split by what the value IS: the PATH must survive EXACTLY (both minifiers collapse `"; "` and space runs), while the type/encoding names compare WITHOUT whitespace (both minifiers comma-pack an assembly display name and `Type.GetType`/`Encoding.GetEncoding` parse either spelling - same judgement as the `WbemClassObjectUnmarshal`/minify note). The restrictive XAML reader drops it SILENTLY (see the `RestrictiveXamlXmlReader` note). Also, two interactive-editor gotchas surfaced by this gadget's default being variant 2: (a) a gadget whose DEFAULT variant is not the first it lists must declare `GadgetVariant.AsDefault()`, or the editor pre-selects a different payload than the same command line builds; (b) a variant that genuinely refuses `-t` must declare `GadgetVariant.WithoutSelfTest()`, because the shared `test` toggle carries over ON from another module and pressing Generate on a refusing variant would otherwise dead-end on the `-t` refusal - the editor reads the flag to HIDE and stop emitting `test` for that variant (CollectGadget guard), while the CLI still refuses a scripted `-t` out loud. `WbemClassObjectUnmarshal` variant 2 is the remaining user of the flag (its unparsed-blob-into-native-COM `-t` stays refused). ResXFileRef ORIGINALLY used it on variants 2/3 but the maintainer then flipped ResXFileRef to accept `-t` on every variant (self-exploit is the point, see the `-t` note above), so it declares no `WithoutSelfTest` now - the flag/editor mechanism outlived that particular use. - The instinct on a converter-reachable type is that a JSON/YAML member could name it; the whole framework has no settable member of that type, so the ROOT is the only way in and that closes the list to XAML text plus a YAML tag.

- 2026-07-29 - A FIRE ROW ON A TYPE-SPOOF GADGET PROVES THE EVASION BUT NOT THE REBUILD, because the inner gadget is materialised from the member records BEFORE the root object is constructed. `DataTableTypeSpoof` fires even with a BOGUS `--target-type` over a real assembly (the inner TFRP runs, then throws its ObjectDataProvider->Brush cast, aborting before the root ctor). So the ten fire rows only prove the name got past resolution and the `[Serializable]` check - the evasion. The SECOND half of the claim (the named subclass rebuilds a real `DataTable` through its inherited ctor, which matters when the target CASTS the root to `DataTable`) needs a BENIGN cell so the round trip finishes: `SpoofedSubclassNameRebuildsARealDataTable` serializes a test-owned `ISerializable` carrier that writes DataTable's member set under the subclass name, holding a plain string, and asserts the result IS a `DataTable` of the named type with the row intact - on BF and Soap. Behavioural evasion proof mirrors the TCD binder test: `DataTableTypeSpoofEvadesADataTableBlockingBinder` blocks only `System.Data.DataTable`, shows the plain gadget dies and the spoof fires. MEASURED NAME RULES (4.8.1, -t into a marker): the assembly MUST exist on the target (only names travel; the target resolves them); the type MUST be `[Serializable]` (SqlConnection and EntityDataSourceViewSchema resolve but are rejected - confirming the plan's "unusable" verdict on the latter); and SOAP IS STRICT while BF IS LENIENT on the assembly identity - a partial name or wrong `Version=` fires on BF and silently produces NOTHING on Soap. Best real-world names are typed-DataSet tables (`TypedTableBase<T>` subclasses, `[Serializable]`, one per table), nested so the wire name uses `+`: `App.Data.OrdersDataSet+OrdersDataTable`. - The gadget's own `AdditionalInfo`/docs claim "the target rebuilds it through the inherited ctor", and until the benign-carrier test existed nothing proved that half; a green fire row looked like proof and was not.

- 2026-07-29 - NAMING A REAL SUBCLASS ON THE WIRE IS A COMPLETE GADGET ON ITS OWN, and an `internal` one works. `DataTableTypeSpoof` ships the `DataTable` carrier byte-identically and only replaces the type record, because a subclass inherits the protected `DataTable(SerializationInfo, StreamingContext)` constructor that rebuilds the rows. Four things made it cheap and one of them is the load-bearing surprise. (1) `internal` IS NOT A BLOCKER: BinaryFormatter resolves the type with `Assembly.GetType` (which sees internal types) and finds the serialization constructor with `NonPublic` binding, so `System.Data.Entity.Design.SsdlGenerator.TableDetailsCollection` (`[Serializable] internal sealed`, in the full .NET Framework, not the Client Profile) binds and fires on all five advertised cells - proven by fire rows, never assumed. Its sibling `RelationshipDetailsCollection` has the same shape. Both call base FIRST and their only post-call work is re-binding `DataColumn` fields, which cannot throw on a missing column. (2) DELEGATE `GetObjectData` RATHER THAN HAND-COPYING THE KEYS: `DataTable.GetObjectData` is public and virtual, the member set IS DataTable's binary remoting schema (dozens of `DataTable.DataColumn_0.*` plus a `DataTable_0.Records` ArrayList derived from the live table), so a hand-written key list would be a reimplementation that drifts from the framework and reads worse. This is the one documented exception to "every member name and their order live in the gadget file"; the header comment has to say so or the next reviewer reads it as a shortcut. (3) THE MARSHAL DOES NOT ESCAPE THE MINIFY LIMIT: the minifying BinaryFormatter still throws `NullReferenceException` walking the live DataTable graph, measured per formatter, so BF/Los keep the DeepCopy that minifies only the inner XAML. (4) IT IS NOT `DataSetTypeSpoof`: that appends `, x=]` and relies on binder parsing while the type stays `System.Data.DataSet`. Public precedent for the subclass form is CVE-2025-23120 (watchTowr, Veeam), where the application's OWN DataSet subclasses walked through a deny list naming only the base type - which is also the argument for the free-form `--target-type`/`--target-assembly`, since `--inherits DataSet` over the whole 4.8.1 GAC returns nothing.

- 2026-07-29 - A VARIANT THAT ONLY CHANGES A MEMBER NAME COSTS NOTHING TO EXTEND ACROSS EVERY FORMATTER, and `WindowsIdentity` is the clean measurement: `ClaimsIdentity.Deserialize` reaches an unbindered `BinaryFormatter` on exactly three `SerializationInfo` names (`System.Security.ClaimsIdentity.actor`, `.bootstrapContext`, `.claims` - the rest of the switch is plain `info.GetString`), the gadget now offers all three as variants 1/2/3, and all 36 cells (6 formatters x 3 variants x minify) fired. The three keys are interchangeable in EFFECT, so the variant exists for a target that filters or logs on the member NAME, and the honest way to write that is one marshal taking the key plus one private `SerializationInfoKeyForVariant()` that every formatter branch reads - three near-identical marshal classes only pay off when the write ORDER or the member SET differs (which is why `WindowsClaimsIdentity` keeps four). Two traps that are invisible until you look. `WindowsPrincipalGenerator` was CONSTRUCTING `WindowsIdentityIdentityMarshal` from the other gadget's file, so a constructor change broke it - the self-containment rule already forbade that, and the fix (its own `WindowsPrincipalInnerIdentityMarshal`) is byte-identical because the marshal's own class name never reaches the wire. And adding variant 4 to `WindowsClaimsIdentity` made `-g WindowsClaimsIdentity --variant 4 --bgc TypeConfuseDelegate` fail, because a `--bgc` chain forwards ONE option set and the leaf knows only 1-3; that refusal is the good outcome (the alternative is a leaf silently building something else) and it is asserted rather than worked around, with a variant-free leaf (`AxHostState`) used for the bridge test itself. - The instinct is that a second member name needs a second gadget or a narrowed formatter list, and here the whole sink maps onto one gadget with no `.Without` anywhere.

- 2026-07-29 - A VARIANT NUMBER THAT MEANS A DIFFERENT MEMBER ON A DIFFERENT FORMATTER CANNOT BE CAUGHT BY A FIRE ROW, and `WindowsClaimsIdentity` is the case that proves it: on BinaryFormatter/LosFormatter/NDCS variant 1 was the WIF type's own `_actor` member (plus the `m_userToken`/`_label`/`_nameClaimType`/`_roleClaimType` its constructor needs) and 2/3 were `.actor`/`.bootstrapContext`, while on Json.NET/DCS/Soap variant 1 was `.actor`, 2 was `.bootstrapContext` and 3 SILENTLY fell through to 1. All 48 cells fired, so nothing ever failed, nothing flagged it, and the shipped labels said "bootstrapContext member" for a variant writing `.actor` on half the list. THE ASSERTION THAT FINDS THIS is an expected-member table (`ExpectedClaimsKey` in `ysonet.Tests`) checked per (gadget, formatter, variant, minify) cell - present AND the other candidates absent - because every wrong answer still reaches the same sink and still fires. Now unified on the maintainer's call: 1/2/3 are `.actor`/`.bootstrapContext`/`.claims` on every formatter and match the sibling `WindowsIdentity` gadget number for number, and 4 is the WIF `_actor` sink, which declares `Without(Json.NET, DCS, Soap)` because its `IntPtr m_userToken` has no shape in those hand-written documents, so `GuardVariantFormatter` refuses the pair by name instead of falling through. THE RENUMBER WAS FORCED, against the usual rule: `GadgetsDeclareVariants` requires `Variants()` to be exactly 1..N, so retiring 1-3 would leave a gap, and refusing variant 1 would break the DEFAULT invocation on every formatter - the escape hatch that made it acceptable is that all four members reach the same unbindered `BinaryFormatter`, so no EFFECT changed, only the member name (which is what the variant selects). Marshals are now named for what they build, not for a number, so the mapping cannot drift again. - The retired-variant rule assumes the old number can be refused; when the ambiguity sits on variant 1 of a contiguous list, it cannot, and the tie-breaker is whether the effect (not the bytes) is the same.

- 2026-07-29 - THREE MEASURED FACTS BEFORE PUTTING AN `IntPtr`, A HANDLE, OR A `Type` IN AN ISerializable PAYLOAD, because two of them silently cap what the tool can express. (1) YSONET.EXE RUNS 32-BIT. Both AnyCPU configurations leave `Prefer32Bit` at the .NET 4.x default, which is TRUE for an exe, so `IntPtr.Size` is 4 inside the generator and `new IntPtr(long)` cannot hold an address a 64-bit TARGET needs. Never construct the `IntPtr`: emit a nested surrogate that does `info.SetType(typeof(IntPtr))` and `info.AddValue("value", <Int64>)`, which is exactly what `IntPtr`'s own `GetObjectData` writes, and a 32-bit generator then emits a correct 64-bit payload. Declare the member as `typeof(IntPtr)` in the parent's `AddValue` so the wire still says `System.IntPtr`; BF/Soap/Los/NDCS all produce byte-identical output whether the declared type is `IntPtr`, `object`, or left to the runtime type. The matching limit is the TARGET's, not ours, and it is worth asserting rather than hiding: `IntPtr`'s deserialization constructor throws "An IntPtr or UIntPtr with an eight byte value cannot be deserialized on a machine with a four byte word size", so `-t` on a wide address legitimately fails HERE while the payload is still right for a 64-bit target - print a `Debugging.ShowNote` saying so. (2) A `Type` MEMBER TRAVELS AS `System.UnitySerializationHolder` (internal, so `Type.GetType("System.UnitySerializationHolder")`; members `Data` = full type name, `UnityType` = 4 for `RuntimeTypeUnity`, `AssemblyName` = display name). Emitting that holder yourself is what keeps the operator's type name from being resolved on the OPERATOR's machine: `GetRealObject` does `Assembly.Load(AssemblyName).GetType(Data)` on the READER, or `Type.GetType(Data)` when `AssemblyName` is empty. JSON.NET IS THE EXCEPTION and it fails loudly: it compares the `$type` against the member's DECLARED type first and reports "Type specified in JSON 'System.UnitySerializationHolder...' is not compatible with 'System.RuntimeType...'", but it DOES accept a bare assembly-qualified STRING and converts it. So a `Type` member needs two renderings, not one. (3) `SerializationInfo.GetValue(name, type)` returns a null element BEFORE any assignability check, so a null member is always legal however narrow the requested type is - but the entry must still be PRESENT or `GetElement` throws. - Point (1) caps every pointer/handle gadget at 2 GB if you write the obvious code, and it fails as an `OverflowException` inside ysonet that reads like bad operator input.

- 2026-07-29 - BOTH MINIFIERS DELIBERATELY COLLAPSE THE SPACE AFTER A SEPARATOR INSIDE AN ASSEMBLY DISPLAY NAME OR A TYPE NAME, in JSON as well as XML, so a fidelity guard over such a value must compare WITHOUT whitespace or it refuses every `--minify` payload the gadget can build. `XmlMinifier`'s "replacing spaces between things like Microsoft.IdentityModel, Version=..." pass and `JsonMinifier` both turn `mscorlib, Version=4.0.0.0, Culture=neutral, PublicKeyToken=b77a5c561934e089` into the comma-packed form, and that is the point of the pass - `Assembly.Load` and `Type.GetType` parse either spelling, so the collapsed value is INTACT rather than corrupted, the same judgement `WbemClassObjectUnmarshal` already makes for whitespace inside base64. Split the guard by what the value IS: exact comparison for anything positional or numeric (an address, a length, a path), whitespace-insensitive for an identifier grammar. `MinifiedTextGuard.XmlTextValues(xml)` is reusable on its own when the shared `MissingTextValues` equality is too strict, and `MinifiedTextGuard.AsXmlText` returns null for a binary stream so the XML half self-skips. - The first version of the guard was exact for all three values and failed every minified cell on SoapFormatter, NDCS and Json.NET at once, which reads exactly like a broken payload.

- 2026-07-29 - `NetDataContractSerializer` NAMES THE ROOT ELEMENT AFTER THE SERIALIZED OBJECT'S OWN DATA CONTRACT, and a NESTED type's contract name carries its OUTER type - so a marshal declared inside `XxxGenerator` makes every NDCS payload open with `<XxxGenerator.SomeMarshal ...>` and puts the generator's name in every payload an operator ships. The reader never uses that element name (`z:Type` / `z:FactoryType` carry the real target), so it is free to be neutral: keep marshals as SIBLING top-level classes in the gadget's own file, which is what the catalogue already does and which the self-containment rule is satisfied by. It matters most for a module that is not meant to be listed, where the payload would otherwise disclose the module, but it is worth avoiding everywhere. A test that asserts "no marshal name leaks into the payload" therefore has to exempt NDCS and assert the `z:Type` instead; for BF, Soap, Los and a hand written JSON document the wire type IS the target, so a marshal name there means `SetType` silently did nothing. - The generator-class name in a shipped payload is invisible until you read one, and the fix is a file-layout choice made once.

- 2026-07-28 - A READ-ONLY `IXmlSerializable` PROPERTY IS A REACHABLE XAML SINK, and the ONE thing that decides whether it fires is the `<x:XData>` wrapper. `DynamicUpdateMapExtension` is the reference case: a public `MarkupExtension` in `System.Activities` whose `[ContentProperty]` getter lazily builds an internal `NetDataContractXmlSerializable<DynamicUpdateMap>` and whose `IXmlSerializable.ReadXml` runs `new NetDataContractSerializer { AssemblyFormat = Simple }.ReadObject(reader)` with no binder - a XAML-only sink turned into the full NDCS gadget set. Three facts, all read out of the decompiled System.Xaml rather than guessed. (1) `MS.Internal.Xaml.Parser.XamlScanner.IsXDataElement` treats markup as literal XML ONLY for the XAML language's `XData` element, so nesting the inner document straight under `<Type.Property>` makes the parser try to resolve the inner ROOT as a XAML type and it dies with "Cannot create unknown type '{...}string'" without ever reaching the sink; that failure looks exactly like "the technique does not work" and is the single detail worth checking first on any `IXmlSerializable`-property gadget. (2) NO SETTER IS NEEDED, which inverts the usual property-sink question: `XamlObjectWriter.Logic_ApplyPropertyValue` checks `value is XData && prop.Type.IsXData` (`XamlType.LookupIsXData` = `CanAssignTo(IXmlSerializable)`) BEFORE looking for a setter, and `ClrObjectRuntime.SetXmlInstance` then READS the property and calls `ReadXml` on what came back. (3) The `(T)` cast runs AFTER `ReadObject` returns, so the `InvalidCastException` naming the object the inner serializer built is DIRECT EVIDENCE the chain ran - a better assertion anchor than a marker for a benign probe payload. Formatter list is Xaml alone, structurally: no other serializer calls `ReadXml`, the property has no setter and its declared type is an interface with no members, the type is not `[Serializable]`, and a data contract is built from read-write members. Non-XAML delivery is by CHAINING (`-g WorkflowDesigner -bgc DynamicUpdateMapExtension -f Json.NET`), not by widening the list. - Prior work on this bridge shipped the version without `x:XData`, concluded "XamlReader.Load cannot dispatch ReadXml", and papered over it by self-testing the inner blob directly, so the whole technique reads as unreachable unless you know which element the scanner is looking for.

- 2026-07-28 - `RestrictiveXamlXmlReader` IS AN ALLOWLIST, NOT THE FIVE-TYPE BLOCKLIST IT LOOKS LIKE, and reading it the wrong way round produces a false capability claim. The CVE-2020-0605/0606 mitigation (`XamlReader.Load(XmlReader, useRestrictiveXamlReader: true)`, used by the WPF clipboard and XPS sinks; ysonet exposes it as `SerializersHelper.Xaml_deserialize_restrictive`) names `ObjectDataProvider`, `ResourceDictionary`, `AssemblyInstaller`, `WorkflowDesigner` and `BindingSource` in `_restrictedTypes`, so a new XAML carrier absent from that list reads as a bypass. It is not: `IsRestrictedType` keeps a type ONLY when it is a `DependencyObject` subclass whose namespace is `System.Windows[.*]`, a primitive, or allowed via the `XPSAllowedTypes` registry key / `SerializationConfig`, and `Read()` then skips the whole subtree of anything else. So `DynamicUpdateMapExtension` is dropped there, and the failure is the SILENT kind - `Load` returns null, no exception, no effect - which is why "it did not throw" can never stand in for "it fired". Any new non-`System.Windows` XAML gadget is in the same position, so state the limitation rather than testing it again. Where it does NOT apply: `XamlServices.Load`, `ActivityXamlServices.Load` and the plain `XamlReader.Load(XmlReader)` overload all use the default schema context and are unaffected. - The write-up for this gadget claimed it evaded XAML type allowlists, the blocklist reading supported that, and a measurement showed the opposite.

- 2026-07-28 - Three mechanics for embedding one gadget's document inside another's, learned wiring the first NDCS bridge consumer. `GenericGenerator.Serialize` returns the NetDataContractSerializer payload as `byte[]` (it writes into a `MemoryStream`), NOT a string, so a consumer that assumes `as string` gets null - accept both. An embedded document must have any leading XML declaration STRIPPED, because a declaration is legal only at the very start of a document and one in the middle makes the whole outer payload unparseable. And `--minify` renames namespace PREFIXES (`z:` -> `c:`, and the outer `x:` -> `a:`) and drops a `z:Type` that a `z:FactoryType` already implies, so a test that asserts the inner payload survived must match prefix-free tokens (`DelegateSerializationHolder`, `SortedSet`, `:Type=`) or it fails on the minified cell only. On the test side, `BridgeLeafFor` in `ysonet.Tests` needed a new NetDataContractSerializer row: it throws for an unknown bridged formatter on purpose, so the first consumer to declare one fails both bridge sweeps until the leaf is named. - Each of the four is invisible until the exact cell that hits it fails, and the byte[]/string one fails at generation with a message that sounds like the inner gadget is broken.

- 2026-07-28 - A WRITE-ONLY PROPERTY IS A SECOND, INDEPENDENT FILTER ON THE FORMATTER LIST, and it is far more generous than it looks. `WorkflowDesigner` is the reference case: `System.Activities.Presentation.WorkflowDesigner.PropertyInspectorFontAndColorData` has a SETTER AND NO GETTER, and the setter runs `XamlReader.Load` on its value (then casts to `Hashtable`; `XmlResolver` is null, so it is NOT an XXE path). The usual property-setter question ("does this serializer assign members by name?") is only half of it - the other half is whether the serializer's member list is built from a read-AND-write contract, because such a serializer never SEES the member, names the type correctly, constructs it and assigns nothing. MEASURED, 16/16 cells firing into a real sink: Json.NET (`JsonProperty.Writable`), Xaml, FastJson, JavaScriptSerializer (`GetProperty` + `GetSetMethod`), both SharpSerializer modes (`PropertyDeserializer` looks the name up at assignment time), and both MessagePack Typeless flavours (`EmittableMember` keeps a setter-only member) ALL reach it. Only YamlDotNet fails for the write-only reason - its deserializer inspects types through a readable-properties inspector that filters on `CanRead` - and it THROWS rather than failing silently, which is the better of the two failures. BF/Soap/Los/FsPickler are out for the unrelated `!Type.IsSerializable` reason, and the DataContract family plus XmlSerializer for the read-write-contract reason. THE TRAP THAT NEARLY KILLED THE PLAN: a serialize-then-deserialize SHAPE PROBE reports "not reached" for EVERY serializer on a write-only member, and that result is meaningless - no serializer emits a member it cannot read, so the deserializer never sees it. ysonet hand-writes its documents, so the only valid measurement is deserialize-only against a document that already carries the member (`ysonet.Tests/WriteOnlyMemberProbe.cs` is the permanent A/B, paired with a Json.NET control). - The round-trip probe said 0/5 and the real answer is 8/9; acting on the probe would have withdrawn a gadget that reaches seven formatters more than the payload it replaced.

- 2026-07-28 - RETIRING A GADGET VARIANT: REFUSE THE OLD NUMBER BY NAME, do not renumber the survivors and do not let it fall through. `ObjectDataProvider` lost two payloads on the same day (variant 3, the `ResourceDictionary Source=URL` fetch, and variant 4, the `WorkflowDesigner` wrapper), each because it wore this gadget's name while needing something the gadget does not - a different EFFECT for one, a different target ASSEMBLY (`System.Activities.Presentation`, which ODP's facets must not declare) for the other. The first attempt renumbered 4 down to 3 to keep the list `1..N` contiguous, and that is the wrong instinct: a number that used to mean something else is exactly how a scripted `--var 3` silently builds a different payload. `RefuseRetiredVariant()` now throws for 3 and 4 with a message naming the replacement gadget, and it is called at the TOP of `Generate()` rather than inside the Xaml branch, because the variant is parsed before the formatter branch is chosen and a guard inside that branch would let `-f Json.NET --var 4` through. The catalogue-wide "variants are exactly 1..N" invariant (`GadgetsDeclareVariants`) still holds, because the survivors already were 1 and 2. - A gap in the numbering is cheap; a reused number is a silent wrong payload, and the contiguity rule reads as if it demands the renumber.

- 2026-07-28 - `SelfTestNeedsStaThread` (on `GenericGenerator`, twin of `SelfTestNeedsChildProcess`) is how a gadget whose TARGET can only be built on an STA thread gets a working `-t`. Added with `WorkflowDesigner`, whose constructor builds WPF objects and creates a `System.Windows.Application` when the process has none, so on a plain worker thread it throws before the member is ever assigned and the gadget reads as broken. It replaced an ad-hoc STA block inside `ObjectDataProviderGenerator` that only ever served the wrapper payload, and it is deliberately INDEPENDENT of the child-process hook: one is about the target's threading requirement, the other about not killing ysonet. - The mechanic is not gadget-specific, so it belongs in the base class; leaving it inline meant every future WPF-constructing gadget would copy the same thread dance.

- 2026-07-28 - THE DENIAL-OF-SERVICE CONTRACT NOW LIVES IN ONE PLACE, `ysonet/Generators/README.md` -> "Denial of service: one facet, and everything it turns on", and the create-gadget skill, the create-plan `making-a-gadget.md` reference and `docs/ARCHITECTURE.md` all point at it instead of restating it.
