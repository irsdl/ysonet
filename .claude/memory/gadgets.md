# Gadgets (ysonet/Generators/)

- 2026-07-28 - THE DENIAL-OF-SERVICE CONTRACT NOW LIVES IN ONE PLACE, `ysonet/Generators/README.md` -> "Denial of service: one facet, and everything it turns on", and the create-gadget skill, the create-plan `making-a-gadget.md` reference and `docs/ARCHITECTURE.md` all point at it instead of restating it. Written after the first DoS gadget shipped, because the rules were scattered across a plan, a safeguards note and three skills and would have drifted the moment a second one was added. The switch is ONE declaration - `PayloadKind.DenialOfService` in `Facets()`, on the gadget or on a single variant - and `DosPolicy` derives everything from facets with no name list, so a gadget can never be half-covered; never add a second mechanism beside it. Free: the `--i-understand-dos` refusal (preflighted in `PayloadRunner`, backstopped in `GenerateWithInit`), both bulk exclusions with a printed skip count, the NORMAL/FULL matrix skips and the fire-helper hard failure, the `--dos` generation-only tier, the `!! DENIAL OF SERVICE` preview line, and the acknowledgement SETTING the interactive editor offers only while such a gadget is selected. NOT free, and these are the ones to get right: `-t` via `SelfTestNeedsChildProcess`/`IsolatedSelfTest` with `PayloadReader.CanRead` covering every advertised formatter (that is what decides self-test vs refusal), one printed line before the child dies, never a row in any fire list, a short `AdditionalInfo()` because the shared banner already carries the authorization wording, and per-formatter effect evidence from an operator-run harness. THE TOGGLE RULE: the acknowledgement is required on every surface and WORDED for the surface - the CLI says "re-run with --i-understand-dos", the editor names the SETTING through its normal "not ready to generate" block (`DosPolicy.EditorBlockedMessage`), and interactive use must NEVER imply it. Both wordings live in `DosPolicy` so they cannot drift. - Declaring it only when disruption is the PURPOSE is the other half: a conditional side effect belongs in `AdditionalInfo()`, or the acknowledgement becomes a box people tick out of habit.

- 2026-07-28 - A GADGET WHOSE PAYLOAD IS ONLY A TYPE NAME GETS THE WIDEST FORMATTER LIST IN THE CATALOGUE, and the usual structural question does not apply. `WSManPluginInstance` (the first `PayloadKind.DenialOfService` gadget) instantiates `System.Management.Automation.Remoting.WSManPluginManagedEntryInstanceWrapper` and sets NOTHING: its finalizer calls `Dispose(false)` -> `initDelegateHandle.Free()` on a handle only `GetEntryDelegate` ever allocates, so an object a deserializer built throws `InvalidOperationException("Handle is not initialized.")` on the finalizer thread and the process dies. Because there is no member to place, the "does this serializer drive an ISerializable constructor or set properties by name?" split that decides `DataViewManagerXxe` vs `WbemClassObjectUnmarshal` is irrelevant - 13 formatters all work (Json.NET, Xaml, FastJson, JavaScriptSerializer, YamlDotNet, both SharpSerializer modes, both MessagePack typeless flavours, DCS, DataContractJsonSerializer, NDCS, XmlSerializer), proven as 26 cells (x minify) each ending in a dead CHILD process. Only four are out and both reasons are structural, not unexplored: BF/Soap/Los all read through mscorlib's `ObjectReader`, whose `CheckSerializable` rejects a type with no `[Serializable]` attribute BEFORE it creates anything (so check `Type.IsSerializable` before listing them for any non-attributed target - no document shape helps), and FsPickler refuses the TYPE during pickler resolution with `NonSerializableTypeException` - the same refusal as `FileSystemInfo` but a different cause (that one was `MarshalByRefObject`, this one is the missing attribute), and visible ONLY in the innermost exception. Two more facts worth reusing: the XAML document must use `assembly=<simple name>` because the xmlns takes an assembly NAME and not a display name, so an `--assembly` override deliberately does not reach it; and DataContractJsonSerializer's payload is literally `{}`, which is honest rather than broken - that format names no type and the CONSUMER's declared root type decides what is built. - The instinct on a non-`[Serializable]` target is that the formatter list will be short, and here it is the opposite; the two impossible reasons are also the only two that generalise to any future "just construct this type" gadget.

- 2026-07-28 - THE RUNTIME VERSION AXIS STAYS `unspecified` WHEN THE GATE IS AN ASSEMBLY, and `WSManPluginInstance` is the clean example of the case the DataViewManagerXxe entry below is NOT. An unhandled finalizer exception has terminated the process on every framework this tool targets, so no build gates the effect; what decides whether the payload lands is whether the target resolves Windows PowerShell's `System.Management.Automation` (3.0.0.0 GAC identity, verified on Windows PowerShell 5.1; PowerShell 7 is a different identity and is not claimed). That is a LIBRARY condition, so it belongs in `AdditionalInfo()` and the facet is honestly empty; the gadget declares `GadgetRequirement.ExtraAssembly` instead, and a test asserts the `unspecified` so the decision is recorded rather than looking like nobody looked. Read the two entries together before filling the axis: an `unspecified` beside an `AdditionalInfo()` that names a FRAMEWORK threshold is a defect, and one beside an `AdditionalInfo()` that names an ASSEMBLY is correct. - "Every new gadget must name a working version" is a rule about runtime-GATED gadgets, and applying it to a library-gated one would mean inventing a range.

- 2026-07-28 - A TARGET THAT DERIVES FROM `MarshalByRefObject` LOSES FsPickler, and nothing about the sink predicts it. `FileSystemInfo` (so `DirectoryInfo`/`FileInfo`) has an ISerializable-constructor sink, which is the shape FsPickler normally drives - it is exactly what `DataSetXxe` ships - yet FsPickler refuses it during PICKLER RESOLUTION with `NonSerializableTypeException: Type 'System.IO.DirectoryInfo' is not serializable`, before it reads a single member, so no document shape can work around it. The discriminator is the BASE CLASS, not the interface: `System.Data.DataSet` derives from `MarshalByValueComponent` (by value) while `FileSystemInfo` derives from `MarshalByRefObject`, and FsPickler treats a marshal-by-reference type as unsupported. Check `Type.IsMarshalByRef` before putting FsPickler in a formatter list. The opposite surprise on the same gadget: `DataContractJsonSerializer` DOES reach an ISerializable constructor - it is in `FileSystemInfo`'s list - so the `WbemClassObjectUnmarshal` exclusion was never about DCJS and ISerializable, only about DCJS being unable to express a `byte[]` MEMBER (a base64 string gives "Invalid cast from System.String to System.Byte[]"). Two plain string members are fine. Locked by `FileSystemInfoDeclaresItsFacets`, which asserts both directions and reproduces the FsPickler refusal from a hand written document. - Both facts read the wrong way round from the sink alone, and each one costs or gains a whole formatter.

- 2026-07-28 - `FileSystemInfo`'s trigger rule, read out of `LongPathHelper.Normalize` rather than guessed, because two halves of it are easy to get wrong: mscorlib calls `GetLongPathNameW` when some path COMPONENT contains `~` AND is at most 12 characters. The LAST component counts (the same length test runs after the scan loop), so `\\host\share\aaaaaa~1` fires and a rule demanding a trailing component would reject a working payload; and the scan starts just after the leading `\\`, so the HOST is a component like any other and `\\host~1\share\file` fires too. The plan for the gadget had both wrong. Per the maintainer's call the gadget REFUSES none of it - what a target's path handling accepts is what the gadget is FOR, the same reasoning that stripped `DataSetXxe` variant 2's validation - and instead prints a `--debugmode` note when the value cannot trigger the expansion. `ShortNameExpansionApplies` is internal so the tests check the same rule the product applies. - A shape rule that looks obvious rejected two paths that really do call out, and a refusal would have blocked exactly the research the tool exists for.

- 2026-07-28 - RULE: OPERATOR INPUT IS DOCUMENTED, NOT POLICED. Unless the maintainer asks for validation, a gadget takes `-c` and every option value as typed and checks only that a required one is not empty; no path shape, URL/scheme, host form, extension, character set, or assembly identity check. What the value MEANS is the target's decision, ysonet never opens or resolves it, and a refusal only blocks the experiment the gadget exists for. Teach the proven form in the option help, one line of `AdditionalInfo()` and `docs/usage-and-examples.md`; a generation-time hint goes through `Debugging.ShowNote` (debug-only stderr, so an embedding tool merging streams still captures pure payload) and is never a refusal. Refuse only what cannot be EMITTED: an empty required input, a formatter/variant combination with no branch, an option belonging to another variant. THREE THINGS ARE NOT THIS RULE and stay: escaping the value for the format it lands in, the `--minify` corruption guard (`MinifiedTextGuard` - there the tool genuinely cannot deliver what was typed), and SCOPE decisions about what a gadget is (keeping `WSManPluginInstance`'s type fixed instead of becoming a generic type-instantiation tool is not input validation). Written into `ysonet/Generators/README.md` ("Operator input: document it, do not police it"), the create-gadget and create-plan skills, and section 3b of the plans index; `DataSetXxe`/`DataViewManagerXxe` (see the entry below) already follow it, and so does the in-progress `FileSystemInfoGenerator` in the working tree. - Every plan so far reached for a validator by reflex, and the DataSetXxe one shipped a check that refused a bare Windows path and banned the `%` its own error message told the operator to use.

- 2026-07-28 - The `-t` rule has THREE outcomes, not two, and the third is what a denial-of-service gadget needs. ACCEPT is the default and covers every callback gadget (the corrected 2026-07-27 entry below). ISOLATE is for a payload that takes down whatever process deserializes it: `SelfTestNeedsChildProcess` + `Helpers/Core/IsolatedSelfTest.cs` already exist for the TypeConfuseDelegate XAML wrapper, so a DoS gadget routes `-t` there - the child gets the exact bytes the user gets, the child dies, ysonet reports it - instead of refusing. REFUSE is last: operator data destroyed, operator code run, operator bytes into native code, or the isolated route genuinely cannot run (today `IsolatedSelfTest.Deserialize` knows only BF/Los/Soap/NDCS, and an asynchronous finalizer effect needs a forced collection in the child, so a DoS gadget on a hand-written format has to extend it first). The plans had drifted the other way: the `FileSystemInfo` plan called refusing `-t` "mandatory local safety" for what is only a CALLOUT, and the `WSManPluginInstance` plan refused outright without noticing the child-process route. What made the FileSystemInfo one look defensible is a genuine rule that lives somewhere else entirely: the TEST HARNESS never touches a UNC path unless `YSONET_INTERACTSH_SERVER` names a server the operator declared they own, because Windows sends authentication material over SMB. That gates unattended runs, not the product, and OPSEC on a jump box is a docs warning rather than a refusal. - A harness safety rule wearing a product refusal's clothes is hard to argue with and quietly makes one gadget behave unlike the rest of the catalogue.

- 2026-07-28 - THE RUNTIME VERSION AXIS DESCRIBES THE TARGET, and asking "which target property" is what stops the whole axis going wrong. Usually it is the framework the target PROCESS RUNS ON. When the gate is a compile-time compatibility switch it is the framework the target APPLICATION WAS BUILT AGAINST: `XmlReaderSettings.EnableLegacyXmlSettings()` reads the ENTRY assembly's `TargetFrameworkAttribute` once per process, so `DataViewManagerXxe` and `DataSetXxe` fire against an app stamped below 4.5.2 on a fully patched 4.8.1 box and never against one stamped 4.5.2+, on any build. Both were left `unspecified` for weeks on the reasoning that "the gate is not a CLR build" - true, and the wrong conclusion: a compile-time framework threshold is still a version, and leaving it empty hid a known 4.0 - 4.5.1 span behind "nobody looked" and kept both gadgets out of the version filter. They now declare it (variant 2 repeats it, because a facet override replaces the whole set). The harness had the same bug and it MATTERED: `RuntimeBuild.RecordFired` attributed every fire to the machine's `NDP\v4\Full` build, so a row firing into a TFM-stamped child credited 4.8.1 to a 4.5.1-only chain - it now takes an explicit token (`LegacyXmlChild.LegacyVersionToken`) and `VersionEvidenceMatchesThisRuntime` compares each gadget against what IT fired on. Without that fix the suite would have nagged forever to raise the ceiling to 4.8.1, i.e. to undo the correct declaration. - The operator's question is never "what does ysonet run on", and the one FULL-run advisory that would have caught it was drowned out by two permanent false positives.

- 2026-07-28 - RULE: every new runtime-gated gadget plan and implementation names at least one evidence-backed WORKING runtime version. The version describes the target (normally its process runtime, or its `TargetFrameworkAttribute` for a compile-time compatibility gate), never ysonet's build. Test current/latest first; if it does not fire because of runtime compatibility, reproduce on older supported target versions, use the HIGHEST verified working version as the `WithVersions` ceiling, and record the latest tested non-working version as a limitation. Use one token when only one version is established and `RuntimeVersion.Range` only when evidence supports the whole contiguous span. A non-runtime gate (OS patch, library, config) remains `unspecified`; a new runtime-gated gadget with no known working version is unverified and unfinished, never guessed. - A failed latest-version run cannot tell an operator which older target works, and treating latest as the ceiling would make the category metadata false.

- 2026-07-28 - VALIDATING THE FORM OF A TARGET-SIDE IDENTIFIER IS THE WRONG DEFAULT for a research tool, and `DataSetXxe` variant 2 dropped all of it on the maintainer's call: `-c`, `--file` and `--dtd-out` now keep only a "not empty" check (the shared `DtdSystemLiteral.RequireRawValue`, whose message no longer says `--rawinput` because variant 2 has no such flag). Two things were wrong with the strict version. It refused a bare Windows path, a UNC path and any non-http DTD host, when what resolves as a system identifier is the TARGET parser's decision and finding that out is what the gadget is FOR. And its `--file` guard banned `%` while its own refusal message told the operator to percent-encode spaces, so `file:///C:/Program%20Files/x.txt` was rejected by the advice it gave. The XML fact that settles it: a SystemLiteral recognises NO references at all, so `%` and `&` are literal inside `<!ENTITY % file SYSTEM "...">` and only `"` really breaks the DTD by ending the literal. The separate `& % ' #` list still stands - that one is about the CONTENT of the disclosed file, which IS substituted into an entity value and a URI. `--dtd-out` likewise replaces an existing file (`FileMode.Create`, reported on stderr) and creates a missing folder. What actually protects the operator is not a refusal but the ORDER: the companion DTD is written only after the payload serializes, so a failed run leaves an existing file byte-identical, and only a file THIS call created is deleted when the write itself fails. - A refusal on the operator's own path buys nothing here (nothing local is ever opened) and blocks the research, while the order-of-operations guarantee is what a "never destroys your file" promise really rests on.

- 2026-07-27 - RULE for a module that must not be LISTED (a gadget with `GadgetTags.Private` in `Labels()`, a plugin whose `IsPrivate()` returns true): the filter goes on the LISTING side only, never on the lookup side. Both registries are split by that one rule - a name that is PRINTED goes through a listing method (`GetGadgetNames`, `GetGadgetNameClassPairs`, `GetGadgetsContaining`, `GetGadgetsSupportingFormatter`, and the plugin twins plus `GetPluginsWithDescriptions`/`GetPluginsWithCredits`), each taking `includePrivate` defaulted to FALSE so a surface that forgets it shows nothing private; a name that is RESOLVED goes through a lookup method (`GadgetExists`, `ValidateAndGetExactGadgetName`, `GetClassNameFromGadgetName`, `CreateGadgetInstance`, `GetGadgetInfo`, ...) which has no such parameter at all. That is what makes "typing the full command still builds it" true by construction rather than by care, and it is why the renames stopped at the six methods whose name contained "All" (a `GetAll*` that excludes something is exactly the quiet lie the write-it-to-be-read rule exists to prevent). Everything downstream inherits the same defaulted parameter: `GadgetFacetReader.ExpandAll`, `GadgetCategoryQuery.ValidFormatterTokens`/`TryParse`, `GadgetCategoryCommand`, `CliListing`, `Program`, and on the UI side `Wizard` -> `ModuleEditor` -> `CategoryFilterModel.Load`. The decision that is easy to get backwards: an UNREADABLE declaration fails OPEN (listed as public, reason kept on the cached info and printed only under `--debugmode`), because fail-closed would let a broken PUBLIC gadget vanish from `--help` and hide a build error behind a display feature. Abstract base types the reflection sweep also picks up (`GenericGenerator`) can never be constructed, which is normal, so they are excluded from that diagnostic or every debug run prints a false alarm. - A visibility rule that can reach the generation path breaks the one thing the feature promises, and one that can swallow a build error is worse than the noise it removes.

- 2026-07-27 - `System.Data.DataSet` is BOTH `ISerializable` AND `IXmlSerializable`, and which one a serializer honours decides the whole formatter list - measured for `DataSetXxe`, whose sink is the `XmlSchema` member the deserialization constructor hands to a legacy `XmlTextReader`. BinaryFormatter, SoapFormatter, LosFormatter, Json.NET and FsPickler all drive the CONSTRUCTOR and fire. The whole DataContract family does NOT, because DataContract's contract resolution checks `IXmlSerializable` BEFORE `ISerializable`, builds an `XmlDataContract` and drives `DataSet.ReadXml` instead - and the failure is the dangerous silent kind: NDCS and DCS return a real DataSet with NO exception and NO effect (only DataContractJsonSerializer throws). NDCS is the trap specifically, because the WRITE side looks perfect - it honours `info.SetType` and emits `z:FactoryType="d1p1:DataSet" z:Type="System.Data.DataSet"` with the members in no namespace - so a generation-only check, or a "did it throw" check, passes. The discriminator that settles it in one step: put a REAL XSD in `XmlSchema`, deserialize, and require the resulting DataSet to carry the TABLE that schema declares; 1 table means the constructor ran, 0 means it did not. Two more measured facts: Json.NET works despite shipping a built-in `DataSetConverter` (with `TypeNameHandling` on and a declared root of `object`, the ISerializable contract wins), but its document MUST carry `XmlDiffGram` or the constructor throws "Member 'XmlDiffGram' was not found"; and FsPickler's `serializationEntries` entry for a STRING carries the value DIRECTLY, not in the `{"Value": ...}` object wrapper a `byte[]` entry needs (see the `WbemClassObjectUnmarshal` note). - Two of the plan's expectations were wrong in opposite directions, and an empty-but-valid DataSet is exactly what a matrix row would have reported as a pass.
- 2026-07-27 - The two XXE carriers are the reference case for "same gate, opposite formatter family", so neither list generalises to the other: `DataViewManagerXxe`'s sink is a property SETTER (Xaml, JavaScriptSerializer, FastJson, both SharpSerializer modes) and `DataSetXxe`'s is the ISerializable CONSTRUCTOR (BF, Soap, Los, Json.NET, FsPickler). The gate they share is not the installed CLR build but the deserializing APPLICATION's `TargetFrameworkAttribute`, which `XmlReaderSettings.EnableLegacyXmlSettings()` reads once per process, so both declare the TARGET-side span `net-fx-4.0 .. net-fx-4.5.1` (see the 2026-07-28 entry; they were wrongly `unspecified` until 2026-07-28). Both were kept standalone rather than folded into one gadget with two variants, because a `--variant` that silently swaps the carrier TYPE and the whole formatter set is misleading, and unifying them would have meant un-shipping the already-released `DataViewManagerXxe` name. The URL check is the only shared part and it moved to `Helpers/Input/DtdSystemLiteral.cs` (names no gadget; takes the module name and example as arguments); the document template stayed per-gadget because it is the payload. Neither gadget uses the shared `RawInputOption` help - its wording says formatter-layer escaping is off, which is NOT what their `--rawinput` does: it skips ONLY the URL validation, and the finished XML is still escaped for the outer document. - The instinct on a second carrier for the same vulnerability class is to make it a variant, and here that would have hidden a completely different formatter set behind one name.
- 2026-07-27 - A gadget earns `PayloadKind.InformationDisclosure` only from a test that recovers CONTENT, never from observing a request, and `DataSetXxe` variant 2 is the first in this catalogue to do it. Measured limits on 4.8.1 against a 4.5.1-targeted app, and they are sharper than "big files fail": spaces, CRLF, `<`, `>` and `"` all arrive PERCENT-ENCODED and decode cleanly, and 4 KB came back intact, but `&`, `%`, `'` or `#` anywhere in the file produces NO result at all (the first two start entity references, `'` ends the inner quoted literal, `#` starts a URI fragment). That is the real explanation for the published "system.ini yes, web.config no" asymmetry - it is the CHARACTER SET, not the size. That variant is also this catalogue's first gadget side effect on the operator's disk: `--dtd-out` uses `FileMode.CreateNew` and UTF-8 with no BOM (the target has no XML declaration to learn an encoding from), never creates a folder, and everything is validated and the payload serialized BEFORE the file is touched, so a bad input or an unsupported formatter leaves nothing behind. The generic FULL matrix then needs a per-cell destination, because sharing one path would correctly fail the second cell. - "XXE" is read as file disclosure by default, so the facet needs the content-recovering test, and the limits are what an operator actually has to plan around.

- 2026-07-27 - RULE for `-t`: refuse it only when a self-test would DAMAGE OR COMPROMISE THE OPERATOR'S MACHINE - destroy their data, run their code, hand unparsed bytes to native code, or kill ysonet. Do NOT refuse merely because deserializing calls out to the network: `-t` means "deserialize it here so I can see the effect", and for a callback gadget seeing the callback IS the effect. Measured across the catalogue: of the seven gadgets declaring `PayloadKind.Network`, five accept `-t` while really calling out (`DataViewManagerXxe` fetches its external DTD, `PictureBox` and `InfiniteProgressPage` load their URL, `ObjRef` builds the remoting proxy); the only refusals are `AssemblyInstallerLoad` (loads and runs the operator's DLL), `TempFileCollection` (deletes the operator's files) and `WbemClassObjectUnmarshal` variant 2 (unparsed operator bytes into a native COM unmarshaller). `WbemClassObjectUnmarshal` shipped refusing BOTH variants, inherited from a plan written while the effect was still unclassified, and that was simply wrong for variant 1 - the maintainer noticed because `-t` behaved unlike every other gadget. The split is now per VARIANT, which is the right granularity: the dividing line is WHOSE bytes are in the payload, not what the payload does. Verified the allowed half really works by watching this machine's DNS cache gain the host after a `-t` run, for all seven formatters - a stack-trace grep is NOT a good check here, because `Debugging.ShowErrors` prints only the OUTER exception for some formatters, so the inner `CoUnmarshalInterface` frame is invisible even when the sink ran. - A safety refusal that is stricter than the rest of the catalogue reads as a bug to the user, and the plan-era wording ("performs the operator-supplied effect inside ysonet") would refuse `-t` on half the network gadgets if applied literally.

- 2026-07-27 - RULE: when a gadget offers BOTH a "ysonet builds the bytes for you" variant and a "bring your own bytes" variant, name and document them by WHO WRITES THE BYTES, never by what they might achieve - and say outright what the BYO variant is NOT. Readers default to assuming the BYO variant is the ESCALATION (the RCE one, the "stronger" one), because that is how a bring-your-own-DLL gadget like `AssemblyInstallerLoad` really does work, and because the published research on a chain is usually the exotic memory-corruption end of it rather than the boring one shipped here. `WbemClassObjectUnmarshal` is the reference case: both variants do the identical thing to the target (hand a `byte[]` to `CoUnmarshalInterface`) and differ only in whether the OBJREF is built from a host name or read from the operator's file, yet the maintainer read variant 2 as "leads to RCE" from the first wording. That is evidence the wording was at fault, not the reader. What fixed it: variant LABELS phrased as "Call out to a host: ysonet builds the OBJREF for you" and "Bring your own blob: ship the file in -c byte for byte - NOT a code-execution variant", an option-help paragraph that opens with "BOTH variants do the same thing to the target ... and differ only in WHO writes those bytes", and a header block spelling out that the BYO variant is an escape hatch for a blob the built one cannot express. Facets must agree: a BYO variant declares `PayloadKind.Other` and inherits NOTHING from the built variant's proven kind, because the operator's bytes decide the effect - and if those bytes happen to be the same shape the built variant emits, it behaves identically and the tool cannot know. - A variant list is read as a menu of increasing power unless it explicitly says it is not, and an over-claimed variant is exactly the kind of misinformation the metadata rules exist to stop.

- 2026-07-27 - RULE: when a gadget's sink is inside the ISerializable CONSTRUCTOR, the formatter audit is decided before you test anything: only serializers that INVOKE that constructor can fire it, and a serializer that rebuilds the object by setting fields or properties BY NAME can never do so, however well it names the type. `WbemClassObjectUnmarshal` is the reference case - `IWbemClassObjectFreeThreaded.DeserializeFromBlob` is called from nowhere but the `(SerializationInfo, StreamingContext)` constructor - and it is the exact INVERSE of `DataViewManagerXxe`, whose sink is a property SETTER and where the property-based serializers are the ones that work and the runtime formatters are out. So check WHERE the sink lives before writing `SupportedFormatters()`; the two cases have opposite answers and neither generalises. Measured result: BF, Soap, Los, NDCS, DCS, Json.NET and FsPickler reach it; Xaml, XmlSerializer, JavaScriptSerializer, YamlDotNet, FastJson, both SharpSerializer modes and both MessagePack typeless flavours cannot, and DataContractJsonSerializer fails for a second, independent reason (it cannot express a `byte[]` for an ISerializable member at all - a base64 string gives "Invalid cast from System.String to System.Byte[]" and an array gives "Object must implement IConvertible"). - Two of the plan's own starting expectations were wrong in opposite directions, and the structural rule settles the whole axis in one step instead of sixteen experiments.
- 2026-07-27 - Three shapes for an ISerializable target carrying ONE `byte[]` member, all measured rather than guessed: NDCS needs NO special document - the plain `SetType` marshal works, because the TARGET is itself `ISerializable` (this is the other half of the 2026-07-26 TempFileCollection note, where the target was a plain `[Serializable]` class and NDCS/DCS therefore needed a separate `[DataContract]` shape; check which kind your target is first). DCS needs the member as `<flatWbemClassObject i:type="x:base64Binary" xmlns="">` inside the usual `<root type="...">` envelope. Json.NET needs the member as a base64 STRING (`[1,2,3]` and a `$type`/`$values` wrapper both fail); its own serializer is useless here because it writes `$type` from the marshal's runtime type and ignores `SerializationInfo.SetType`, so the document is hand written. FsPickler's `serializationEntries` entry for a `byte[]` is NOT a base64 string at that level: `"Type": {"Case":"Array","ElementType":{"Case":"NamedType","Name":"System.Byte",...}}` with `"Value": {"Value":"<base64>"}`. The reliable way to find any of these is to ask the serializer itself to write an equivalent local ISerializable stand-in and read what it emits. - Each one is a document nobody can derive by reading the target, and the failure is always a cast or parse error that points nowhere near the real cause.
- 2026-07-27 - Two COM/DCOM facts a payload built on `CoUnmarshalInterface` depends on. (1) Capturing a real marshalled `IWbemClassObject` gives you an `OBJREF_CUSTOM` (flags `0x04`, custom marshaler CLSID `4590f812-1d3a-11d0-891f-00aa004b2e24`, ~21 KB) that carries the WMI object BY VALUE and names no host at all - so no captured blob can ever produce a network callback, which is why the published research on this type went to OBJREF_CUSTOM memory corruption instead. An `OBJREF_STANDARD` ([MS-DCOM] 2.2.18) has to be built from scratch; its `DUALSTRINGARRAY` names the host and an unknown OXID forces the target to resolve it remotely. (2) The RPC endpoint inside a string binding IS IGNORED for OXID resolution, which always uses port 135: `127.0.0.1[18136]` never reached a listener bound to 18136, it just failed as an unusable binding. So the gadget REFUSES `host:135` / `host[135]` rather than stripping them, and a test-owned local endpoint is impossible because RPCSS owns 135. - The port point looks like a detail and actually decides the input type, the validation, and whether the effect can be tested without leaving the machine.

- 2026-07-27 - RULE: pick the JSON escaper by the QUOTE CHARACTER of the template the value lands in, not by the gadget. The shared `EscapeForJson`/`CommandArgSplitter.JsonStringEscape` (and `CommandType.JSON` for a value going through `SplitCommand`) also writes a single quote as `\'`, which exists only for the many templates in this project built from SINGLE quoted strings (Json.NET accepts those). `\'` is not a legal escape in ANY JSON, and the parsers disagree: Json.NET and JavaScriptSerializer read it back as a literal quote, but fastJSON DELETES the character, so `C:\John's dir\x.dll` silently becomes `C:\Johns dir\x.dll` and the target loads a different file. For a DOUBLE quoted template (also correct for a double quoted YAML scalar) use `CommandArgSplitter.JsonDoubleQuotedStringEscape`, exposed as `GenericGenerator.EscapeForJsonDoubleQuoted`, or `CommandType.JSONDoubleQuoted` when the value travels through `SplitCommand`. Swept the whole catalogue on 2026-07-27, so no double quoted template emits `\'` any more: `AssemblyInstallerLoad` (Json.NET/JavaScriptSerializer/FastJson/YamlDotNet), `DataViewManagerXxe` (JavaScriptSerializer + FastJson), `PictureBox` and `InfiniteProgressPage` (FastJson + YamlDotNet), `FileLogTraceListener` (FastJson + YamlDotNet + DataContractJsonSerializer), and `ObjectDataProvider` (FastJson + FsPickler).
