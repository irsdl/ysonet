2026-08-06 - REWRITING THE ASSEMBLY IDENTITIES IN A PAYLOAD IS A ONE-FIELD TRANSFORM, AND THE THING IT IS MOST USEFUL FOR IS EXPOSING THE REAL BLOCKER. Three rules the measurements forced. (1) THE VERSION NUMBERS ARE MEASURED, NOT REMEMBERED: read them from the generation's own reference assemblies and re-check the table against the machine the suite runs on, because two in-box assemblies follow their PRODUCT number rather than the framework one, and a handful of framework assemblies have no old-generation build at all - where the transform must REFUSE rather than emit a payload that cannot bind. (2) OPERATOR DATA AND PAYLOAD IDENTITY ARE INDISTINGUISHABLE IN THE FINISHED BYTES, so restricting the rewrite to "serializer-owned positions" is the wrong defence: it leaves a full identity sitting in element text (a serialization holder stores the assembly it wants as an ordinary string member) and the option then does nothing on exactly the readers that need it. (3) THE REWRITE OFTEN CHANGES THE ANSWER RATHER THAN THE OUTCOME: a chain classified "our payload names a newer assembly version" was, once the identity was fixed, refused for naming a TYPE the old framework does not have - so the identity was never the whole story, and the pair of measurements is the deliverable. - Each of the three was a wrong first guess: the version table, the positional restriction, and "fixing the identity will make it fire".

Do NOT confuse this with the Release binary's string encryption (`ysonet/obfuscar.xml`), an antivirus false-positive measure on one shipped exe, off in Debug and via `-p:ObfuscateRelease=false`, which never changes how source is written. Written into `ysonet/Generators/README.md` + `ysonet/Plugins/README.md`, `CLAUDE.md`, `docs/ARCHITECTURE.md` section 5, and the create-gadget/create-plan/consistency-check skills. - The point of the project is that someone else can read a chain and reproduce it; a clever compact payload costs a researcher a decompiler session.
