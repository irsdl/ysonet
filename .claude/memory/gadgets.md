# Gadgets (ysonet/Generators/)

- 2026-07-26 - A payload template written with DOUBLE quotes must NOT escape with the shared `EscapeForJson`/`CommandArgSplitter.JsonStringEscape`: that one also writes a single quote as `\'`, which exists only for the templates built from SINGLE quoted strings (Json.NET accepts those). `\'` is not a legal escape in ANY JSON, and the three parsers disagree about it - Json.NET and JavaScriptSerializer read it back as a literal quote, but fastJSON DELETES the character, so `C:\John's dir\x.dll` silently becomes `C:\Johns dir\x.dll` and the target loads a different file. New `CommandArgSplitter.JsonDoubleQuotedStringEscape` (exposed as `GenericGenerator.EscapeForJsonDoubleQuoted`) escapes only `\` and `"`, which is also correct for a double quoted YAML scalar. `AssemblyInstallerLoad` uses it on its Json.NET/JavaScriptSerializer/FastJson/YamlDotNet branches and locks it with `AssemblyInstallerLoadEscapesOperatorPaths`. Still on the old escaper and carrying the same latent bug for a value containing `'`: `DataViewManagerXxe` (JSS + FastJson) and `PictureBox`/`InfiniteProgressPage`/`FileLogTraceListener` (FastJson) - see `dev-kitchen/todo/`. - Generation succeeds, the payload is valid JSON, and only one of the three parsers is wrong, so nothing fails until an operator uses a path with an apostrophe.
- 2026-07-26 - `--minify` corruption is NOT an XML-only problem: `YamlMinifier` collapses a run of spaces, so `C:\two  spaces\x.dll` comes back naming a different file, while the XML minifier's `"; "` collapse happens to leave the same path alone. So a gadget delivering operator DATA must verify EVERY text branch, not just the XML ones. `AssemblyInstallerLoad.PathSurvived` splits three ways: `MinifiedTextGuard` for Xaml/SharpSerializerXml (parse and compare), a plain "the escaped rendering is still present" check for the JSON and YAML documents, and nothing for the two binary formats (`MinifyHandWrittenPayload` returns a byte payload untouched). `MinifiedTextGuard.XmlTextValues` now also collects ATTRIBUTE values, because a gadget that puts its value in an attribute (Xaml `Path="..."`, SharpSerializer `<Simple value="..."/>`) was invisible to it and every check reported "missing". - The existing rule said "verify, do not predict" but the shared helper could only see text nodes and only XML, so two thirds of the exposure had no check at all.
- 2026-07-26 - The four WinForms getter-call carriers are NOT interchangeable across serializers, and the dividing line is one property: `PropertyGrid.SelectedObjects` has a SETTER, while `ComboBox`/`ListBox`/`CheckedListBox` expose `Items` as a read-only collection. Measured for `AssemblyInstallerLoad`: Json.NET and Xaml build all four (both can ADD to a read-only collection), and FastJson, JavaScriptSerializer, YamlDotNet, SharpSerializerXml/Binary and MessagePack typeless build only PropertyGrid. The failure is the dangerous kind: FastJson and JavaScriptSerializer return a real ComboBox with an EMPTY `Items`, so the payload deserializes cleanly and simply never calls the getter (YamlDotNet and SharpSerializer at least throw). That is why the gadget REFUSES `--getter 2..4` on those formatters instead of silently emitting them. Same split applies to any future getter-chain gadget, so it does not need re-measuring. - The old getter gadgets only ever shipped PropertyGrid outside Json.NET/Xaml and never wrote down why.
- 2026-07-26 - `CommandInputType.UncPath` (derives `PayloadInput.UncPath`) exists for a gadget whose input must BE a UNC path, not merely accept one - added with `AssemblyInstallerLoad` variant 2, which refuses a local path while variant 1 refuses a UNC one. It is what makes two same-shape variants meaningful rather than decorative: the wizard prompts for the right thing and the FULL matrix feeds each variant a sample of its own type (`SampleInputForGadget`). Do not add a competing value; the `FileSystemInfo` plan is expected to reuse it. Adding a value still means updating every exhaustive site - `GadgetFacetReader.DeriveInput`, `Wizard.InputTypeName/CommandLabel/CommandHelp` and its `candidateTypes` list, `ModuleEditor.CommandExample`, and the tests' `SampleInputForGadget`. - Without a distinct input type a variant can only be a label, because nothing downstream (prompt, sample, validation) can tell the two apart.

- 2026-07-26 - RULE: a gadget's payload lives in the gadget's own file, all of it - templates, target type names, member names AND their order, and any surrogate shape (nested type in the generator class). A helper or `GenericGenerator` may only hold mechanics that name no gadget, taking the names/shapes as arguments and storing none. The one allowed cross-gadget dependency is reusing another GADGET as the inner payload via `GenerateInner` (declared with `Bridged`/`Hosted`). What this replaced: `Generators/NonRceGadgetPayloadBuilder.cs` (a non-gadget class sitting in the gadget folder that held four gadgets' templates) and three MessagePack "gadget builder" helpers with their surrogate POCOs (`MessagePackNonRceGadgetHelper`, `MessagePackObjectDataProviderHelper`, `MessagePackGetterSettingsPropertyValueHelper` + `*Surrogates.cs`). The generic parts became `GenericGenerator.HandWritten.cs` (`FinishHandWrittenPayload` = minify by format then self-test through the existing `RunSelfTest`, plus `RequireCommandInput`, `RawInputOption`, `EscapeForJson`/`EscapeForXmlAttribute`, `IsFormatter`/`IsMessagePackTypeless`/`IsMessagePackLz4`, `UnsupportedFormatter`) and `Helpers/MessagePack/MessagePackTypelessTypeSwap.cs` (the twin of the existing `SharpSerializerTypeSwap`). Contract is public in `ysonet/Generators/README.md`, mirrored in `docs/ARCHITECTURE.md` section 5. - Stripping the tool to one gadget must be possible by deleting the other generator files, and a shared payload builder makes an edit for one gadget silently change another.
- 2026-07-26 - RULE: gadgets and plugins are RESEARCH MATERIAL and must be understandable from their own source by a human and by an AI. The payload stays fully visible: a whole document in a verbatim string with the target type names spelled out, copyable straight into the testing arena (`Helpers/TestingArena/TestingArenaHome.cs`, which exists for exactly that) or a scratch project. Never obfuscate/encode/compress a payload in SOURCE - no base64 blob or byte array standing in for a readable document, no string built from fragments or `char` codes, no reflection avoiding a nameable type, no one document split across methods; when the WIRE needs encoding or compression (the `--compressed` assembly chain, the base64 `SerializedValue` form) build it from readable source at generation time and comment what the bytes are. Real target/member names, technique-derived variable names, comments on the WHY (sink, why the order or member set matters, target-side condition, what silently breaks) not the syntax, straightforward code over a compact trick, and truthful credits with the CVE/reference. Do NOT confuse this with the Release binary's string encryption (`ysonet/obfuscar.xml`), an antivirus false-positive measure on one shipped exe, off in Debug and via `-p:ObfuscateRelease=false`, which never changes how source is written. Written into `ysonet/Generators/README.md` + `ysonet/Plugins/README.md`, `CLAUDE.md`, `docs/ARCHITECTURE.md` section 5, and the create-gadget/create-plan/consistency-check skills. - The point of the project is that someone else can read a chain and reproduce it; a clever compact payload costs a researcher a decompiler session.
- 2026-07-26 - MessagePack Typeless writes a type name ONLY where the member's static type is `object` (the root passed as `object`, and `object`/`object[]` members); a concretely typed member travels as a bare map and the target resolves it from the real property's declared type. So `ObjectDataProvider`'s swap map needed only 2 entries, not 3 - the `ProcessStartInfo` entry had been dead since it was written, because `ProcessSurrogate.StartInfo` is declared as the surrogate type. The swap failing is SILENT: the payload still generates and is still valid MessagePack, it just carries a ysonet surrogate name no target can resolve. `MessagePackTypelessCarriesTargetTypeNames` reads the emitted bytes for all four MessagePack gadgets (target names present, no `Surrogate` leak) - the uncompressed flavour only, since Lz4 is compressed; PictureBox's Lz4 rows are fired end to end in `PayloadsFireIntoTestSinks`. - Generation success proves nothing for a bait-and-switch payload, so a surrogate rename/move needs a byte-level assertion, not a matrix row.

- 2026-07-26 - An `ISerializable` marshal with `info.SetType(target)` reaches the runtime formatters but NOT the DataContract pair, and the reason is the member NAMESPACE: DCS/NDCS write an ISerializable object's members in NO namespace, which is right when the target is itself `ISerializable` (`AxHost.State`, `TextFormattingRunProperties`) and wrong when it is a plain `[Serializable]` class, whose contract puts the members in the type's own data-contract namespace and in ALPHABETICAL order. `TempFileCollection` hit this as `Error in line 1 position N. 'EndElement' ... is not expected. Expecting element 'basePath'`. The fix that generalises: serialize a second, INERT `[DataContract(Name=..., Namespace=...)]` shape whose contract name, namespace and `[DataMember(Name=...)]` values are already the target's (no `Order`, so the alphabetical default matches), then for NDCS retarget only the ROOT tag's `z:Type`/`z:Assembly`, and for DCS ship it as-is inside the project's `<root type="...">` envelope because plain DCS carries no type info at all. Do NOT reuse `SerializersHelper.NetDataContractSerializer_Marshal_2_MainType` for a gadget that carries operator DATA: its `Replace(":" + prefix, "")` pass runs over the WHOLE document and would corrupt a Windows path containing `:a`. Bonus finding: DCS serializes a `Hashtable` member as a `KeyValueOfanyTypeanyType` collection (not as ISerializable members), and the target still reads it. - Two of the five formatters on the first field-serialized (non-ISerializable) framework type in the catalog needed a completely different shape, and the failure message points at a missing member rather than at a namespace.
- 2026-07-26 - `--minify` is not the only thing that rewrites operator text: `SerializersHelper.DataContractSerializer_serialize` writes through an `XmlWriter` with the default `NewLineHandling`, which emits a carriage return RAW, so every XML parser then normalizes it away - with no minification involved. So a gadget delivering a value the target uses literally must verify EVERY payload, not just the minified ones. The shared mechanics now live in `Helpers/Serialization/MinifiedTextGuard.cs` (`MissingTextValues` over the serialized document); each gadget keeps its own refusal wording because the alternative it can offer differs. `TypeConfuseDelegateFileOperations` was repointed at it and kept its exact message (locked by `FileOperationsRefuseLossyMinification`); `TempFileCollection` uses it with two messages, one naming `--minify` and one naming the XML writer. Trap while wiring it: the probe serialization must keep `Minify` ON (a `DeepCopy` that clears it silently checks the wrong document and the guard never fires). Better still, when `-t` is refused `Serialize()` has no side effect, so serialize ONCE, guard the result, and return it. - The instinct is "guard the minifier"; half the corruption is in the writer.

- 2026-07-25 - The ObjectDataProvider Xaml payload must NOT ship `IsInitialLoadEnabled="False"` - the generator sets `odp.IsInitialLoadEnabled = false` before assigning `ObjectInstance` so that BUILDING the payload does not invoke the method inside ysonet itself, but `XamlWriter.Save` then wrote that property into the payload, where it suppresses the initial load on the target. A host that parses the XAML on a WPF/STA (dispatcher) thread therefore did nothing at all: no exception, no execution. Only the `--minify` path was correct, because its discardable-regex list happened to drop the attribute - which is why the minified fire row passed while the plain one failed. Fixed with `DropInitialLoadSuppressor` applied to the emitted XAML (and to the variant 4 bridge) so the live object keeps the flag and the payload does not. Same `odp.IsInitialLoadEnabled = false` pattern exists in `TextFormattingRunPropertiesGenerator` and `XamlImageInfo`, which still rely on the minify-only discard - worth the same treatment. The SharpSerializer path is safe (it excludes every ODP property except MethodName/ObjectInstance). - A self-protection flag set during generation must never leak into the emitted payload.

- 2026-07-24 - A gadget or plugin that hardcodes which INNER gadget it wraps must call `GenerateInner(formatter, inputArgs)` (on `GenericGenerator`), never `GenerateWithNoTest`. `Init` parses `inputArgs.ExtraArguments` for whichever generator it runs on, so passing the caller's own args down hands the inner gadget the OUTER module's flags; `GenerateInner` clears `ExtraArguments` while keeping the command, Minify, UseSimpleType, debug mode, and `ExtraInternalArguments` (the deliberate steer-the-inner channel used by TextFormattingRunProperties' xamlurl hand-off and SharePointPlugin). Keep `GenerateWithNoTest` only where the gadget was chosen by the USER via `-g` (ViewState, SharePoint, Resx), because there the forwarding is the point. Found when `TypeConfuseDelegate` gained a `var|variant`: `-g GetterSecurityException --variant 4` started failing, and `-g WindowsClaimsIdentity --variant 3` had been silently turning its inner ObjectDataProvider into the SSRF variant long before that. Guard: `EveryVariantGeneratesFromTheVariantFlagAlone` generates every declared variant with the variant flag and nothing else. - The option namespace is shared across one `-g` invocation, so a new option name on a widely reused leaf gadget collides with every outer gadget using that name. `GadgetFullMatrixGenerates` catches only the hard-failure half, and it masks the rest by always passing `--xamlurl`; the silent-wrong-payload half is caught by nothing, so isolate at the call site rather than relying on tests.
- 2026-07-25 - `GadgetTags.Hosted` (renamed from `GadgetTags.Variant` on 2026-07-25) marks a gadget that serializes NO type of its own: it builds a payload body and hands another generator's object to `Serialize()`. Those files live in `ysonet/Generators/HostedPayloads/` (namespace stays `ysonet.Generators`; discovery is reflection over `IGenerator` and ignores namespaces) with the contract in that folder's `README.md`. Membership test is what reaches `Serialize()`: another generator's object means hosted, its own `*Marshal` class or a framework type means a normal gadget in `Generators/`. Only two members: `XamlAssemblyLoadFromFile` and `ActivitySurrogateDisableTypeCheck`, both a XAML `ResourceDictionary` carried by `TypeConfuseDelegateGenerator.GetXamlGadget` (variant 1) or `TextFormattingRunPropertiesMarshal` (variant 2). It does NOT mean the generator has a `Variants()` list: `TypeConfuseDelegate` keeps `Independent` and `DataTable` keeps an empty `Labels()` even though both expose a `var/variant` selector. - The old name collided with `GadgetVariant`/`Variants()`/`--variant` and needed six separate disambiguation notes across code, memory and plans; the folder plus the new name replace them, and the create-gadget, create-plan and consistency-check skills now carry the rule.
- 2026-07-24 - The `(N)` suffix inside a `SupportedFormatters()` token (e.g. `"BinaryFormatter (3)"`) is a hand-written annotation meaning "this formatter carries N variants". Everything that consumes formatters (`IsSupported`, `CliListing.Formatters`, `GadgetFacetReader.CleanFormatter`, the full matrix) splits on the first space, so the suffix is display-only. `docs/gadgets-and-plugins.md` mirrors it and documents the convention. - It is the only place the public catalog discloses that a gadget has variants; a multi-variant gadget without it looks single-variant in the snapshot. Counts are PER FORMATTER, not per gadget (`WindowsClaimsIdentity` is the reference case). As of 2026-07-25 EVERY multi-variant gadget is annotated, so a missing suffix is a new defect, not a backlog item: `DataTable`, `XamlAssemblyLoadFromFile`, `ActivitySurrogateDisableTypeCheck`, then the remaining eight (`GetterSettingsPropertyValue` Json.NET+Xaml 4 but MessagePack bare because `Generate()` forces variant 1, `GetterSecurityException` 4, `GetterCompilerResults` 4 (its .NET-version difference is a target property, not a variant), `XamlImageInfo` 2, `ResourceSet` 2 on all three via the `ig` option, `GenericPrincipal` 2 on BF/Los/Soap but bare on the three DataContract paths which ignore the variant, `DataSetOldBehaviour` 2, `DataSetOldBehaviourFromFile` 2). The consistency-check skill audits the count against code and both docs.
- 2026-07-24 - SoapFormatter cannot serialize a generic type, so no `SortedSet<T>` / `SortedDictionary<K,V>` / `TreeSet<T>` root can ever carry a SoapFormatter payload. This is why `TypeConfuseDelegate` advertises only BinaryFormatter, NetDataContractSerializer and LosFormatter, and why the gadgets that wrap a TCD inner declare `.Without(Formatters.SoapFormatter)` on that variant. Locked by `TypeConfuseDelegateContainersCannotUseSoapFormatter`. - Saves re-running the formatter audit for any future container-shaped variant of this gadget.
- 2026-07-25 - `AdditionalInfo()` is the FIRST block of the interactive info panel, and the panel only renders `BodyRows` lines - a long one silently pushes `Formatters:`, `Command input:` and the category summary off the visible area. Keep it to one or two short sentences and put the detail in the option help text (which `--fullhelp` and the editor both show). Caught by `ModuleInfoPanelShowsFacts`, which drives the module list and asserts `Command input:` is still on screen for the FIRST gadget alphabetically (`ActivitySurrogateDisableTypeCheck`) - so that gadget is the canary for this, and a failure there means some gadget's info text grew, not that the panel broke. - A doc-style change to one string can delete facts from a UI screen with no error anywhere.
- 2026-07-25 - A gadget variant can declare the OPTIONS it does not use, with `GadgetVariant.WithoutOptions("name")` (canonical long name), the gadget-side counterpart of a plugin mode's option list. `ModuleEditor.ApplyVariantOptionScope` hides those settings while that variant is selected AND `CollectGadget` drops their values, so a value carried across modules in `OptionMemory` can never leak into the emitted command line (the same guard `--bgc` and the DoS acknowledgement already had). The CLI still parses the option and ignores it, so no scripted command breaks. Only the two `HostedPayloads` gadgets declare anything today (variant 2 does not use `rootcontainer`); a variant that declares nothing keeps every option, so no other gadget is affected. - Without the `CollectGadget` half, hiding a field would be cosmetic and the stale value would still ship in the command.
- 2026-07-25 - The TypeConfuseDelegate XAML path (`GetXamlGadget`) fires through ALL THREE container roots, and unlike the command path it needs no distinct-key guard - on deserialize the sorted root inserts the SMALLER element first and compares the larger against it, so the spliced method's FIRST argument is always the larger-sorting element. The XAML path's two elements are the XAML document and `""`, and `""` sorts smallest, so the document always lands in arg 1 of `XamlReader.Parse` no matter which container carries it. That is also why the two elements can never collide (a XAML document is never empty), so `RejectEqualKeys` stays a command-path-only concern. Proven, not assumed: `XamlContainersEvadeSortedSetBinder` fires containers 2 and 3 through the SortedSet-name-blocking binder. Exposed as `--rootcontainer` on the two `HostedPayloads` gadgets (named that, not `--container`, which reads like a deployment container); the shared builder is `BuildConfusedContainer`. - The ordering rule is the whole reason a two-element type-confusion payload works, and it is invisible in the code.
- 2026-07-26 - The TypeConfuseDelegate splice carries a VOID two-string method just as happily as `Process.Start`: `new Action<string,string>(File.WriteAllText/File.Copy/File.Move)` and `new Action<string,string>(Directory.Move)` all round-trip through `DelegateSerializationHolder` and run on deserialize (45 cells proven: 5 operations x BF/NDCS/Los x all three roots, `TypeConfuseDelegateFileOperations`). The multicast stub reads a return value the void target never set, but nothing consumes it - the container just uses a garbage int for tree ordering AFTER the effect has happened - so the payload does not even throw and `-t` reports cleanly (unlike the command path, which throws casting a `Process` to `int`). `File.Create` was rejected for the empty-file case because it returns an open `FileStream` with `FileShare.None` that the confused call cannot dispose; an empty `File.WriteAllText` creates or truncates and closes its own handle. - Opens the primitive to every two-string BCL sink, not only process launch.
- 2026-07-26 - `BuildConfusedContainer` now takes the BENIGN `Comparison<string>` as a parameter, because that comparison sorts the container HERE at generation time and therefore fixes the sink's argument order on the wire (smaller element is serialized first, so the LARGER one becomes argument 1 on deserialize). The command and XAML paths pass `TypeConfuseDelegateGenerator.CultureSensitiveCompare` (`String.Compare`) to keep every shipped payload byte-identical; a gadget with a REQUIRED argument order must pass `OrdinalCompare` (`String.CompareOrdinal`) so its generation-time guard and the serialized order are the same comparison. Mixing them is the trap: an ordinal guard over a culture-sorted container reverses the arguments whenever the two disagree (`"aa..."` vs `"BB..."` is the reproducer - ordinal says the first is larger, en-US says the second is). Locked by `TypeConfuseDelegateSharedBuilderKeepsTheOriginalGraphs` (byte-for-byte for the command paths, `Compare`-not-`CompareOrdinal` on the wire for the XAML paths) and `FileOperationsOrderingIsOrdinalNotCultural`. - The target's culture is irrelevant; only the operator's is, and that is the non-obvious half.
- 2026-07-26 - `--minify` on an XML formatter is NOT text preserving, so a gadget carrying operator DATA (not just plumbing) cannot assume the strings survive it. Measured on the NetDataContractSerializer path: trailing whitespace is trimmed (`XmlMinifier.XmlXSLTMinifier`'s `string-rtrim`/`string-ltrim` templates run on every text node), a carriage return is lost to the `XmlDocument` load/save line-end normalization (`&#xD;` becomes a real CR, then a later parse drops it), and one dirty-match pass collapses `"a; b"` into `"a;b"`. Interior double spaces and LF-only text with no trailing newline survive. That behaviour is deliberate - it is what shrinks an embedded XAML document - so it was NOT changed; instead `TypeConfuseDelegateFileOperations` VERIFIES after serializing (re-parse the XML, look for both strings as exact text values) and refuses the combination. Verify, do not predict: a "reject a trailing newline" rule would have missed the `"; "` case entirely. BinaryFormatter and LosFormatter carry string records verbatim and are unaffected. Locked by `FileOperationsRefuseLossyMinification` plus an expected-failure cell in `GadgetFullMatrixGenerates`. - Any future gadget that delivers a file, a script or a config through an XML formatter hits this, and the corruption is silent.
- 2026-07-26 - A message about a payload has TWO channels and picking the wrong one breaks other people's tooling: `RunResult.Warnings` is printed to stderr by `Program.cs` BEFORE the payload and is for something the operator must see in a NORMAL run (the DoS banner), while `Debugging.ShowNote(inputArgs, text)` prints only under `--debugmode`, and only to stderr. Default to `ShowNote`. ysonet is embedded as a payload generator by other tools, and a wrapper that merges the streams (`2>&1`) and base64-encodes what it captured would carry a normal-run message straight into the payload field - verified the other way round for the new TypeConfuseDelegate ordering note: with streams merged, a normal run still emits exactly one line of pure base64. `Debugging.ShowErrors` predates the rule and still writes its stack trace to STDOUT; that is only survivable because nobody pipes a debug run. A refusal is not affected by any of this, because it travels on the exit code. - The instinct is "warn the user"; the cost lands on an automated caller nobody in this repo can see.
- 2026-07-26 - `CommandInputType` now says WHOSE file system a path belongs to: `FilePath` is read on the OPERATOR machine while building, `TargetPath` / `TargetPathPair` / `TargetPathAndLocalFile` are only touched by the deserializing process (deriving `PayloadInput.TargetPath`, new alongside `local-file`). `FileLogTraceListener` was migrated from `FilePath` to `TargetPath`: its `-c` is a directory the target creates, so the old prompt "this gadget reads the file" was simply wrong. Adding a value means updating every exhaustive site - `GadgetFacetReader.DeriveInput`, `Wizard.InputTypeName/CommandLabel/CommandHelp/CommandDefault` and its `candidateTypes` sweep list, `ModuleEditor.CommandExample`, and the tests' `SampleInputForGadget` - and `CommandInputTypes`/`InputDerivationCoversCommandInputTypes` now iterate `Enum.GetValues` so a new value cannot silently inherit the shell-command wording. - The distinction is the one thing a user has to get right on a file gadget, and one generic "path" value cannot express it.
- 2026-07-24 - `System.Collections.Generic.TreeSet<T>` (mscorlib, .NET Framework 4.5+) is internal and `[Serializable]`, derives from `SortedSet<T>`, and has a PUBLIC `TreeSet(IComparer<T>)` constructor, so `Activator.CreateInstance` reaches it without private reflection. `SortedDictionary<K,V>` is field-serialized (it does not implement `ISerializable`) and its private `_set` is a `TreeSet<KeyValuePair<K,V>>` whose `KeyValuePairComparer.Compare` forwards to the stored key comparer. Both therefore reach an attacker comparer on deserialize through the inherited `SortedSet` callback. Verified against the .NET 4 GAC graph (see [[framework-research]]). - These are the two container roots that carry the TypeConfuseDelegate splice without emitting a `SortedSet` wire type name.
- 2026-07-26 - A gadget whose sink is a PROPERTY SETTER is gated by one question - does the serializer set properties BY NAME, or does it infer a contract? - and `System.Data.DataViewManager` is the sharp case because it implements `IList`/`IEnumerable`. Measured for `DataViewManagerXxe`: Xaml, JavaScriptSerializer, FastJson, SharpSerializerXml and SharpSerializerBinary all FIRE, while Json.NET (`Cannot deserialize the current JSON object ... because the type requires a JSON array`), YamlDotNet (`Expected 'SequenceStart', got 'MappingStart'`), DataContractSerializer (`Expecting element 'ArrayOfanyType'`), XmlSerializer (`You must implement a default accessor ... because it inherits from ICollection`), NetDataContractSerializer (`cannot be serialized`) and MessagePack typeless all build a COLLECTION contract and never touch the property. Two fail SILENTLY, which is the trap: DataContractJsonSerializer returns a real `DataViewManager` with nothing set, and MessagePack typeless returns a `Dictionary<object,object>` - both look like a working round-trip if you only check for an exception. BinaryFormatter/Soap/Los/FsPickler are out for a second, independent reason (field-based, and the type is not `[Serializable]`). So the plan's "Json.NET, highest confidence" was exactly backwards. - Check the collection interfaces on the carrier BEFORE writing the formatter list, and assert absence of the effect, never absence of a throw.
- 2026-07-26 - SharpSerializer BINARY is reachable for a property-setter gadget that must never construct its target, via `Helpers/SharpSerializer/SharpSerializerTypeSwap.SerializeAs(surrogate, targetAqn)`: serialize a surrogate with the same property names, then rewrite the one type-name record. SizeOptimized mode keeps type names in a CACHE of 7-bit-length-prefixed UTF-8 strings and everything else refers to them by INDEX, so swapping in a longer or shorter name needs no offset fixing anywhere. This is the binary twin of `MessagePackNonRceGadgetHelper.SwapTypeCacheName`, and it closes the one formatter the non-RCE family (PictureBox, InfiniteProgressPage, FileLogTraceListener) had left on the table - those three could all gain it. - The alternative, serializing the live target to get its shape, is exactly what a setter gadget must not do, because the setter IS the effect.
