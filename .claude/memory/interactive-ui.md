# Interactive UI (ysonet/Interactive/)

- 2026-07-29 - A RECOVERED DEFAULT IS EMITTED, SO A TRUNCATED ONE SHIPS A DIFFERENT PAYLOAD - worse than no default at all, because it looks right. `EditableField.ParseDefault` reads the value after a `Default:` marker in the option help (NDesk.Options records nothing; the validation is a compiled lambda), the editor pre-fills the field with it, and `CollectGadget` puts it straight into the argv. `DataTableTypeSpoof` shipped with `Default: System.Data.Entity.Design.SsdlGenerator.TableDetailsCollection` unquoted, the parser broke on the first `.`, and the editor showed AND EMITTED `--target-type System`: a well-formed payload naming a type no target resolves, so `-t` from the editor simply never fired while the identical CLI command did. Two rules come out of it. (1) THE PERIOD RULE IS NOW THE SAME ONE `SegmentAfter` ALREADY USED: a `.` ends the value only when a space or the end of the text follows, so a dotted type name or `payload.resources` survives while `Default: AES. e.g: ...` still stops at the sentence. That also fixed `ResxPlugin --of`, which had been recovering `payload` for years. (2) A COMMA STILL ALWAYS ENDS AN UNQUOTED VALUE, so any default containing one - an assembly display name - MUST be quoted in the help text, which is what the quoted branch is for and what `WSManPluginInstance --assembly` already did. Quoting is the author saying "this whole string is the value". - The truncation is invisible on the CLI, which never reads the help text, so only an interactive user hits it.

- 2026-07-28 - THE OPTION-CHOICE HEURISTIC TURNED ONE VALUE INTO A MENU OF BROKEN FRAGMENTS, because some commas separate the PIECES OF A VALUE rather than alternatives. `EditableField.ParseChoices` -> `ColonList` takes the text after any `:` and `SplitList` splits it on commas, so `WSManPluginInstance`'s "Default: System.Management.Automation, Version=3.0.0.0, Culture=neutral, PublicKeyToken=..." became a picker offering `System.Management.Automation`, `Version=3.0.0.0` and `Culture=neutral` as SELECTABLE VALUES for `--assembly`. Picking any of them produced a payload naming an assembly that does not exist, and the maintainer's report - "Version 3.0... is the same as choosing the asm above it" - is exactly right: every fragment is equally wrong. `PublicKeyToken=...` was missing from the menu only because `LooksLikeToken` caps a token at 30 characters, which is a good reminder that the heuristic's own filters make a misfire look deliberate. Guard: `SplitList` now returns nothing when two or more parts are spaceless `Name=Value` (`AttributeLikeParts`), which is the shape of an assembly display name, a connection string or a URI query tail. Spaces around `=` deliberately do NOT count, so the numbered form ("1 = bare ObjectDataProvider, 2 = ...") still parses. Locked in `OptionHeuristics` with both directions plus the real gadget through `BuildFieldsForTest`, and verified by disabling the guard and watching it fail. Swept the catalogue: no other module's option help carries an assembly display name, so this was reachable through one gadget but the bug was in the shared heuristic. - A choice list is offered with an "(enter a custom value)" escape hatch, so a wrong menu never blocks anyone and nothing fails; it just quietly hands the operator a payload that cannot work.

- 2026-07-28 - A NEWLINE INSIDE A MODULE'S OPTION HELP USED TO STACK THE WHOLE COLUMNS VIEW, and it is the same "menu repeats down the screen" symptom as the entry below with a completely different cause. The columns view redraws in place by counting the lines it wrote and moving the cursor up by that many, so the invariant it rests on is ONE RENDERED LINE = ONE CONSOLE ROW. `ModuleEditor.Wrap()` split on spaces only, so a `\r\n` inside an option's help survived inside a "word", the footer line carrying it occupied TWO rows, `MoveUp` landed one row too low, and every frame leaked another row. Option help is written with `\r\n` in it FOR THE COMMAND-LINE HELP FORMATTER and the editor's footer shows the same string, so most gadgets could trip it; it surfaced on `WSManPluginInstance`'s `assembly` setting, and the giveaway in the screenshot was that every stale block showed that one setting selected. Measured with a per-section cursor trace: the footer consumed 4 rows for its 3 lines. Fixed at the invariant, not at the gadget - `ConsoleCursor.OneRow()` folds control characters to spaces, `PadClear` and `Cell` apply it so no rendered line can move the cursor, and `Wrap` applies it FIRST so multi-line help wraps across the footer instead of being truncated at the newline (PadClear alone would have silently cut the sentence). Locked by `ColumnsNeverStackAtAnyWindowHeight`, which drives the editor at five window heights straddling the frame height. A SECOND, INDEPENDENT off-by-one turned up in the same place and needs a DIFFERENT KIND OF TEST: the frame is 20 lines but needs 21 ROWS, because the newline after the last line lands the cursor one row further on, so a window of exactly `FrameHeight` scrolled every single frame. `ColumnsFit()` allowed it (`>= FrameHeight`); it is now `MinWindowHeight = FrameHeight + 1`. The lesson is why frame inspection could not catch it: once the frame scrolls, the HEADER GOES OFF THE TOP, so "the header appears at most once" is satisfied by a screen that is actively crawling upward - the assertion passed vacuously on broken code. It is asserted directly instead, through `ColumnsFitForTest`/`MinWindowHeightForTest`, and the negative case was verified by reintroducing the off-by-one and watching the test fail. - The virtual terminal could not have caught this by luck: it only wraps on the character AFTER the last column, so only a real embedded newline (not an over-long line) reproduces it, and that is exactly what happened.

- 2026-07-28 - THE MODULE INFO PANEL PRINTS SHORT FACTS FIRST AND THE FORMATTER LIST LAST, because that list is the one block with NO upper bound and the panel renders only `BodyRows` (15) lines. `WSManPluginInstance` advertises 13 formatters, which is 11 of those 15 rows at the narrow 34-char column on its own, so with the old order (`Formatters:` -> `Labels:` -> `Command input:` -> categories) `Command input:` landed around row 25 and NO amount of shortening `AdditionalInfo()` could recover it - the documented "keep AdditionalInfo() to two sentences" rule does not cover a fact whose length the author cannot control. Order is now DoS warning -> info -> `Command input:` -> categories -> bridge formatter -> `Labels:` -> `Formatters:`, on the maintainer's call, and the formatter list is what scrolls for a wide gadget (nothing is lost: `--list formatters`, `--fullhelp` and the editor's own picker show the whole set; `WbemClassObjectUnmarshal` now reports its list scrolling as an `[info]` line instead of failing). The contract is one shared assertion, `AssertInfoPanelKeepsItsFacts`, used by the FileSystemInfo, WbemClassObjectUnmarshal and WSManPluginInstance panel tests: every fact PRESENT, the short ones ON SCREEN, and `Command input:`/`Categories` before `Formatters:` - that last ordering assertion is the part that keeps the first two true for the next wide gadget. - Three copies of the old check existed and all three encoded the old order, so one reordering edit would otherwise have silently pushed the facts off again with no error anywhere.

- 2026-07-22 - Screen-redraw convention: a screen must call `ConsoleCursor.ClearScreen()` once when it is entered or re-entered, then redraw in place with `MoveUp` for navigation within that screen; a sub-screen (e.g. an axis checklist) clears on its own entry and the parent clears again on return, wiping it - never append a screen beneath the previous one. - `MoveUp` only redraws in place within a single screen, so a parent -> child -> parent transition without a clear leaves both drawn and the menu appears twice on a real console (the "menu repeats down the screen" stacking bug; fixed in `CategoryFilter`; canonical note on the `Menu` class comment; full detail in `docs/ARCHITECTURE.md` section 4.1).
- 2026-07-22 - A redirected-console test cannot catch a real-console redraw/stacking bug; write the regression test against the `VirtualTerminal` harness (real cursor control) and assert the screen title never appears on two rows of one captured frame - see `CategoryFilterDoesNotStack`. - Under a redirected console `ClearScreen`/`MoveUp` are no-ops and output just appends, so the stacking is invisible to append-mode tests.
- 2026-07-22 - The `Picker` block now sizes to the window: `Picker.Render` calls `FitSizes` each frame, shrinking the preview to 0 then the list toward 1 row so the whole block (`Overhead` = title+help+search+count) fits in `ConsoleCursor.Height()` (from `Term.WindowHeight`). On a short terminal the fixed ~24-line block used to overflow, so the relative `MoveUp` clamped at row 0 and the title scrolled off / the menu stacked (reported "does not work well when the screen is small"). `Height()` returns 0 when we do not control a real console (redirected/tests), which keeps the full 12+8 block and just appends - so redirected tests are unaffected. Regression: `PickerFitsShortWindow` drives the picker in an 80x12 `VirtualTerminal` and asserts the title, Search line and count line all stay on one screen. Same pattern as `ModuleEditor`'s `FrameHeight`/`ColumnsFit` guard. - A fixed-height redraw block must fit the window or the in-place `MoveUp` desyncs on a small screen.
- 2026-07-22 - The single-panel FALLBACK path (`ModuleEditor.RunFallback` -> `EditForm` -> `EditField`, used on a short/narrow real console as well as redirected output) was missing the clear-on-entry convention that the columns path has, so on a small window screens stacked: the top menu stayed above the module picker, and the module-picker info preview (Formatters/Labels/Credit) plus edit-screen leftovers stayed above the settings form (reported "residuals when I go inside the menu"). Fix: `RunFallback` clears at the top of its loop; `EditForm` clears at the top of its loop (covers the module-preview residual on entry and the edit residual on re-entry); `EditField` clears on entry; action rows (Generate/Show command) clear before running, then `PauseForReview()` (only when `ConsoleCursor.CanControl()`) so the payload/command stays readable before the loop clears. Gating the pause on `CanControl` keeps redirected/tests unchanged (no extra keypress, clears are no-ops there). Regression via a new `DriveFallbackFrames` harness (VirtualTerminal + `ModuleEditor.ForceFallback=true` + real cursor control): `FallbackClearsTopMenuOnShortWindow`, `FallbackFormClearsModulePreview`, `FallbackFormClearsEditResidual`. - Every screen transition on a real console must clear or the previous screen shows as a residual/stack; the columns path already did this, the fallback did not.
- 2026-07-24 - The module editor's built-in `bridgedgadgetchain` (--bgc) field must only show for gadgets that can themselves receive a bridged payload. `--bgc` prepends inner gadgets before the `-g` gadget, and the `-g` gadget is the OUTER consumer, so PayloadRunner requires it to carry `GadgetTags.Bridged` plus a non-empty `SupportedBridgedFormatter()`; for any other gadget (e.g. DataTable, a root carrier with empty `Labels()`) a chain fails at generate with "... is not a bridge gadget and it cannot accept another gadget". `AddCommonTail` still creates `_bridged` (kept non-null so `CollectGadget` is safe) but sets `_bridged.Hidden = !IsBridgeGadget()`; `CollectGadget` also guards `g.Bgc` on `!_bridged.Hidden` (mirrors the `rawcmd` guard) so a value carried across modules in `OptionMemory` is never emitted for a non-bridge gadget. Regression: `BridgedChainShownOnlyForBridgeGadgets`. Audit of the other conditionally-relevant settings found them already gated: `command`/`rawcmd` via `RefreshDynamic` Hidden, `variant` only added when the gadget has variants, plugin `mode` only added when modes exist and its options hidden per `ApplyPluginMode`, `examples` excluded as non-payload; the global flags (minify/usesimpletype/test/debugmode/output/outputpath) apply everywhere. - A built-in that only some modules support must be hidden, not offered-then-failed; field-order-sensitive VirtualTerminal tests (DriveFrames) should navigate by type-to-filter, not `.Down()` counts, so hiding a field does not shift them.
- 2026-07-24 - Per-setting reset in the module editor: a single field can go back to its default without rebuilding the whole module. `EditableField.DefaultValue` is snapshot in `LoadModule` right after `RefreshDynamic()` and before `ApplyRememberedValues()` (so it is the true parsed/seeded default, not a carried-over memory value). `ModuleEditor.ResetFieldToDefault(f)` restores it, clears Touched/ExplicitEmpty, drops the field from `_session.OptionMemory` (so it stops propagating), then calls `RefreshDynamic()`. Two UI gestures drive it: Delete on a focused value row in the columns view (`RunColumns`), and a "(reset to default)" entry appended to every Flag/Choice/Pick edit menu (both `RunColumns`/`CommitChoice` and the fallback `EditField`). The synthetic menu entries are the `CustomValueEntry`/`ResetDefaultEntry` consts, and the shared list is built by `EditorItems`/`EditorStartIndex` so columns and fallback agree. Regression: `SingleFieldResetToDefault`. - The fallback `Picker` list has no Delete-to-reset (it is a generic shared control); the fallback reaches reset via the menu entry instead. - Gives a way to unset a value like `bridgedgadgetchain` that a plain edit could not clear.
- 2026-07-22 - The `Picker` window shows up to 12 rows (fewer on a short window, see the FitSizes note above), so an action/option row appended at the BOTTOM of a long list (e.g. the gadget list's `[ Filter by category... ]`) is off-screen until the user types or scrolls. Make it discoverable another way: a hint in the picker title, a footer/legend key (the live columns add `Ctrl+F`), and rely on type-to-filter surfacing it (typing "filter" narrows to that row). - Bottom placement keeps the first real item as the default selection (good for the common Enter-Enter pick), but trades away default visibility of trailing rows.
- 2026-07-27 - `-i` takes ONE session-wide visibility flag and it must reach four separate surfaces, not just the picker. `Program.Main` dispatches interactive mode before any option parsing, so the flag is read straight from argv (`PrivateModulePolicy.WantsPrivate(args)`) and passed to `InteractiveMode.Run(showPrivate)` -> `Wizard` -> `ModuleEditor` -> `CategoryFilter`. The trap the first draft of the plan missed: showing the right modules in the picker is NOT enough, because `ModuleEditor.FilteredModuleNames` re-runs `GadgetCategoryCommand.MatchingGadgetNames` whenever an in-build category filter is active, and `CategoryFilterModel.Load` expands the whole catalogue again for the checklist - so with only the picker wired, `-i --prv` would show a private gadget and then silently drop it the moment the user opened or applied the filter. `BridgeGadgetNames` (the `--bgc` choices) and the plugins' inner-gadget picker via `FromOption` are two more independent discovery surfaces; both stayed static and take the flag as an explicit parameter rather than reading a field, so no static visibility state exists. The Wizard side is collapsed into one `VisibleGadgetNames()`/`VisiblePluginNames()` pair that the picker, formatter search and run-all all consume, so a future screen cannot forget it. The flag is READ ONLY for the session (no screen can turn it on) and it is in `NonPayloadGlobalOptions`, because it changes listings and never the payload. - Every place that DISCOVERS a module name is its own surface; wiring the obvious one and stopping produces a UI that contradicts itself two keystrokes later.
