# Tooling and repo hygiene

Entry format: date - what - why.

2026-07-23 - Stray .NET `.resources` files (binary, magic `0xBEEFCACE`) named after
GAC assemblies (e.g. `System.Management.resources`) appeared at the repo root during
decompilation work; deleted them and added `/*.resources` to `.gitignore`. - The repo
has zero tracked `.resources`, so any at the root are decompiler/build spillage and must
never be committed. Root cause of the writer is not fully pinned: a local decompile
library (whole-module-to-string) was tested against the exact assemblies and does NOT
leak, so the source is most likely a direct ILSpy/ilspycmd project-mode or resource-dump
run using the repo as its working directory. Rule: run any decompiler from a scratch dir,
never from inside the repo. Open security question (does ILSpy resource extraction allow
path traversal via crafted resource names) is under investigation in `dev-kitchen/dirty/`.

2026-08-01 - In a code-graph `.sqlite` index the `kinds` and `ekinds` id numbers are NOT
stable across databases: each table is written in the order the builder first met each
kind, so id `1` is `class` in one database and `field` in another, and id `2` is
`constructor` in one and `namespace` in another. Any script that reads the tables
directly must resolve every kind by NAME per database (`select id,name from kinds`),
never by a literal id copied from one file. - A hardcoded id does not error, it silently
selects the wrong rows: a sweep over many databases reported ZERO `[Serializable]` types,
zero deserialization constructors and zero findings for whole assemblies that plainly had
them, and the empty result was indistinguishable from a clean one. It also fooled a
hand-written verification query, so the wrong answer got confirmed twice before the
mismatch showed up. Two rules follow: resolve kinds by name, and make a bulk scanner
self-check (a graph with method bodies that resolves zero classes or zero methods is a
mapping fault, and must be REPORTED rather than shown as an all-clear). A query CLI that
already resolves by name is unaffected, so this only bites tooling that opens the
database directly for speed.

2026-08-01 - A code-graph sink pattern must match the TYPE.METHOD tail, never a namespace
prefix, and only CALLABLE nodes may be sinks. Three separate false-result modes were
measured in one bulk scanner. (1) Two naming conventions exist and look identical in a
schema dump: an IL/Cecil-built graph names an external call fully
(`m:system.reflection.assembly.load(system.string)`), while a Roslyn SOURCE-built graph
very often stores only the expression text (`assembly.load`, `_serializer.Deserialize`,
`new ServiceCollection`, `nameof`). Measured: source graphs were 11-17% fully qualified,
IL graphs 95-99%. A pattern anchored on `m:system.` therefore matched NOTHING on the
source graphs and reported them as clean. Fix: anchor on `(?:^|[^a-z0-9_])type\.method`
so both forms match and `myprocess.start` still does not. (2) A namespace-wide or
class-wide pattern is not a sink: `m:system\.directoryservices\.` marked 3,523 nodes
including `ActiveDirectorySecurity.AddAccessRule`, and a bare
`(dynamicmethod|assemblybuilder|ilgenerator)\.` marked every member of those classes.
Name the dangerous METHODS. (3) A sink must be a callable node - restrict by node kind to
method/constructor/property/operator/external. Without that, the FIELD
`DynamicILGenerator.m_scope` and the enum constant `URLACTION_SHELL_SHELLEXECUTE` were
both scored as code-execution sinks, and an unanchored `shellexecute` alternative also
matched the unrelated method `PowershellExecute`. - Each of these fails silently in the
direction that looks like good news (a clean result, or a big impressive hit count), which
is the worst way for a security sweep to be wrong.

2026-08-01 - On a graph that CONTAINS the framework itself, the raw hit count of a
reachability sweep is meaningless and must be filtered to carrier types before it means
anything. Sweeping the whole .NET Framework GAC produced 50,026 "hits" - but the BCL calls
itself constantly, so most of that is framework-internal plumbing rather than anything a
payload can reach. Filtering to types that are actually `[Serializable]` / `ISerializable`
/ `IDeserializationCallback` / `IObjectReference` / `[DataContract]` / `TypeConverter` cut
it to 2,042; requiring the entry member to be one a FORMATTER drives (deser ctor,
serialization callback, finalizer, property setter, TypeConverter, hash/equality) cut it
to 902; tier A cut it to 68. That last list is tractable to read by hand. Sanity check that
the filter is right: the top of it is the canonical published gadget set
(`TextFormattingRunProperties`, `ObjRef`, `DelegateSerializationHolder`, `MethodCall`,
`MethodResponse`, `IWbemClassObjectFreeThreaded`, `SafeSerializationManager`,
`RolePrincipal`), rediscovered independently. - A sweep over a target ASSEMBLY and a sweep
over the FRAMEWORK need different denominators; quoting the unfiltered number from the
second one overstates the work by more than an order of magnitude.

2026-08-02 - There are two reference pages, and a new link belongs on exactly one of them.
The test for `docs/references.md` is "does this show HOW a gadget or plugin was made" - the
research that discovered the technique, and the sources a gadget or plugin points at from
its own file. A CVE database record (NVD), a vendor advisory or patch note, product
documentation (`learn.microsoft.com`, `devblogs.microsoft.com`, `support.microsoft.com`),
and a defensive guide all FAIL that test even when they are accurate and even when a gadget
depends on the behaviour they document: the gadget file already spells that behaviour out,
so the link adds nothing a reader of the gadget does not have. Those, plus tools, uses in
the wild, CTF write-ups and general reading, go in
`docs/dotnet-deserialization-research.md`, which is a strict SUPERSET, so a link added to
the short list must be added to the wide one too. - The two pages were one until a bulk
import took `references.md` from 140 links to 484 and buried the ones the code actually
depends on; trimming it to 30 needed the product-documentation rule as well as the split,
because ten `learn.microsoft.com`-class pages had survived on the strength of a per-gadget
annotation. Before deleting one of those, confirm the fact it carried is in the gadget
source (all four were), or the deletion is lossy. Two gadget files (`DataSetXxeGenerator`,
`WSManPluginInstanceGenerator`) say "see docs/references.md" in a comment, so a link they
rely on must not drift out of the short list. The mechanical check after any edit: extract
the URLs from both pages and from `ysonet/Generators` plus `ysonet/Plugins`, then assert
every cited URL is in `references.md`, every URL anywhere is in the research page, and
`references.md` has no duplicate URL (cross-listing one talk in two sections is how that
creeps in).

host removes them. Of the rest, the product documentation pages a plugin cites fail the
short-list test by the documented placement rule anyway. - Only two halves survive as hard
rules (short list is a subset of the wide page, short list has no duplicate); the
"cited in source but on neither page" set is a review list a human decides, and quoting the
unfiltered version of it reports 66 problems where there are about 20 real ones.

2026-08-02 - A REDIRECT CANNOT BE ADJUDICATED MECHANICALLY, so link tooling must queue
every one of them for a reader rather than follow or reject it on its own. Measured on the
research page: `www.nccgroup.com/research-blog/<slug>` -> `/research/<slug>` keeps the whole
article (adopt the new URL), `research.nccgroup.com/<date>/<slug>` -> `/research/` loses it
(use a snapshot), and `xz.aliyun.com/t/3019` -> `/news/2661` is the SAME article renumbered
by a CMS while sharing 0.00 of its slug. A slug-overlap score sorts that queue but must
never decide it. Two rules for the decision itself: judge the CONTENT (the destination
title and body), and refuse to store a destination URL that looks minted per visit (session
or tracking query key, uuid or long hex path segment, hashbang) unless a human or agent
names a clean address instead - the agent judged the content, and a session URL is exactly
where a content match does not make the address durable. Anything with no live page AND no
snapshot goes to a named "lost links" list; it is never dropped from the document quietly.
- Auto-following a redirect writes a home page into a reading list, and auto-rejecting one
throws away a live article, and the two are indistinguishable without reading the page.

2026-08-02 - When an author has republished vendor-hosted research on their own site, link
the AUTHOR's copy, and the PDF the post hosts when the original was a paper or advisory.
Vendor URLs move: the same NCC Group research has now lived on three hosts
(`nccgroup.trust` paths, `research.nccgroup.com`, `www.nccgroup.com/research-blog`, now
`www.nccgroup.com/research`), two of which are dead, while the author's copies have been
stable. MAINTAINER DECISION 2026-08-02 for this repo: every `soroush.secproject.com` link
and every Soroush-authored NCC link uses `soroush.me` (blog post, or the PDF under
`soroush.me/downloadable/` when the entry stood for a paper); an NCC page by a different
author stays on NCC. - A vendor rebrand silently breaks a whole class of citations at once,
and a snapshot is a worse answer than a live page the author still maintains.

2026-08-02 - Wayback Machine lookups: the CDX endpoint answers
`filter=statuscode:200&limit=-1&fastLatest=true` in about 2 seconds where the exhaustive
`collapse=digest&limit=-5` reverse scan takes 10 to 25, and the slow form is what earns an
HTTP 429. Serialise archive calls behind one lock with a 3 second gap and back off 15/45/90
seconds on 429. - A rate-limited lookup must never be reported as "no snapshot exists":
those two answers send a human to opposite actions (re-run vs go find a replacement by
hand), so any archive tooling has to return them as distinct states.

2026-08-02 - A cache of "healthy" results must not swallow a decision that is still
pending. The research-link checker cached an `ok-redirect` as healthy, and the cached entry
carried no "still needs judging" flag, so 34 redirects silently skipped the adjudication
queue for the whole 30 day cache window while the report still counted them as redirects.
Fix: never cache a result that is awaiting a human or agent decision, cache the DECISION
alongside the result once it exists, and treat a legacy entry with no decision as stale. -
Any check-then-decide tool has this shape, and the failure is invisible: the run looks
clean because the count is still printed, only the work queue is empty.

2026-08-02 - Reading a bot-walled page needs a real browser, and `--dump-dom` is not the
way to get it. On Windows a browser is a GUI subsystem program, so its stdout never reaches
a pipe and the file comes back empty (exit code 0, zero bytes) whichever headless mode is
used. Drive it over the DevTools protocol instead: launch with `--remote-debugging-port=0`,
read the chosen port from `DevToolsActivePort` in the profile directory, then speak CDP over
a WebSocket. Two more measured details: Edge relaunches itself so the launcher process
exiting with 0 means nothing (poll the port file, not the process), and a challenge that
says "Verification successful" still needs seconds before the article replaces it, so the
DOM must be re-read while a wall is on screen or a live page is reported as blocked. -
`scripts/browser_fetch.py` in the research-links skill does this, and it turned all 19
"blocked" links into confirmed live ones: not one had actually rotted.

2026-08-02 - A bot wall tracks the SESSION, not the page, so a batch is what fails, not
the URL. One Medium article opened on its own cleared its challenge; the same article
opened as the fifth tab of one browser session did not, and repeated attempts kept
failing until each URL got a fresh browser profile of its own. Escalate headless ->
visible window -> visible plus a clean profile per URL, with a re-read budget near 80
seconds rather than 20. - This is the difference between "6 links are permanently
unverifiable" and "all 19 are alive", and it is worth trying before anything more
elaborate: the automated click on a "verify you are human" checkbox that looked
necessary was never needed, and automating one is off limits anyway.
- 2026-08-03 - A LOCAL MARKDOWN ARCHIVE OF EVERY CITED SOURCE NOW EXISTS, built by a dev-only tool that READS the two curated reading lists and never writes them; the seven defects it caught in its own machinery are the reusable part. (1) NO CHROME RULE MAY DELETE THE MAJORITY OF A DOCUMENT. A size guard existed on the class/id signal and not on the tag signal, so `<header>` was stripped unconditionally - and several sites wrap the whole article in one (measured: 35,840 of 38,993 characters), leaving the newsletter box as the "article". A tag name and a class name are both just evidence; put both through the same test. (2) A LOSS GUARD IS THE ONLY THING THAT MAKES SUCH A LOSS VISIBLE: the health probe already measured the page's visible text, so compare extraction against it and refuse to publish rather than publishing gutted. Measure the WIDEST candidate, not the chosen one - a precise extractor keeping 3,140 of 20,032 characters of a Stack Overflow page is correct, and comparing the chosen one queued 28 good pages. (3) SETTLE A BROWSER READ ON VISIBLE TEXT, NEVER ON HTML LENGTH: a JavaScript shell is 300 KB the instant it loads, so a length test declared eight pages finished before their article existed (315,652 bytes carrying 171 characters). (4) A TLS HANDSHAKE FAILURE IS A STATEMENT ABOUT THE FETCHER, NOT THE PAGE, exactly like a bot wall: every one in this corpus was a live site a browser opens, so classify it `blocked`, send it to the browser, and never let it select an archive capture. Do not install an accept-all certificate callback to make the number go down. (5) EXTRACTION MUST READ STORED BYTES, so fixing the extractor and reprocessing 500 sources is an offline pass rather than a second crawl, and the re-run describes the document that was preserved rather than whatever the site serves today. (6) PIN A GENERATED FILE NAME ONCE IT EXISTS: counting an entry's own name as taken made every re-run append the next number, and a better title on a re-run silently orphaned the previous file, leaving 70 files nothing pointed at while the folder still looked full. Orphans are a verify failure, not a leftover. (7) A CHECK THAT TESTS THE SHAPE OF A PATH REPORTS RESEARCH MATERIAL AS A LEAK - an archived .NET article is full of `C:\Windows\Temp\payload.dll` - so compare against the REAL machine paths instead, and parse rather than grep when prose is allowed to describe what code may not encode. - Each one produced plausible output while being wrong, and only a measurement caught it: the counts, the probe length, the candidate metrics. A pipeline over hundreds of documents needs something to compare against at every stage, or it fails silently at scale.
- 2026-08-03 - WHEN ONE TOOL CONSUMES ANOTHER TOOL'S OUTPUT, THE CONSUMER OWNS NOTHING: it reads, it reports, and it keeps its own implementation. The archive parses the curated reading lists read-only, has no `link` or `titles` command, and asserts in `verify` that neither document changed during a run; it also imports nothing from the other tool, so a change made for curation cannot break archiving and vice versa. The cost is two URL classifiers in one repository, accepted deliberately and made visible by printing the archive's own classification per URL rather than resolving the disagreement silently. The prompt a user actually wants ("archive this too?") lives in a THIRD, thin wrapper skill that calls both, so neither owner gains a dependency. - The instinct is to reuse the existing checker and have the first tool call the second; that couples two lifecycles and makes the consumer's correctness depend on somebody else's internals.
- 2026-08-03 - A GENERATED FOLDER THAT AGENTS WILL READ FOR YEARS IS ITSELF AN INJECTION SURFACE, so containment cannot stop at generation time: every file carries a banner saying the text below it is untrusted third-party data, the folder index repeats it, and `CLAUDE.md` states the rule for every agent in the repo. The controls that actually hold are structural, not wording: each semantic reviewer is a separate agent definition with an EMPTY tool set, gets one item per invocation in a nonce-fenced block, and may only answer from a closed vocabulary - it cannot supply a URL, a path or a command, so the tool executes actions from candidates it already computed. - Prompt wording is a quality layer and nothing more; an agent that cannot act cannot be talked into acting, which is the only guarantee available.
- 2026-08-04 - IMPORTING HAND-CONVERTED DOCUMENTS INTO A GENERATED ARCHIVE FOUND FOUR MORE DEFECTS OF THE SAME SHAPE, all in code that was already "working". (1) A CLASS NAME IS NOT AN ATTRIBUTE. Scanning a whole opening tag for the word `hidden` matched Drupal's standard body wrapper, `class="field field-name-body field-label-hidden"`, and deleted the article on every Drupal site in the corpus: one saved page went from 132,196 characters of markup to 248 characters of text and was archived as a stub. Parse the element's own attributes and decide from those; a stylesheet-free pass can only honestly read what the element declares about itself. (2) THE WORD YOU TREAT AS NOISE CAN BE THE ONLY DISCRIMINATOR. One conference talk leaves a paper and a deck whose citations differ by a single trailing `whitepaper`, so normalising that word away merged five files from two different PDFs into one group: the two documents were joined into one file and the deck stayed on the unresolved list. The same cut appears in file-name truncation, which eats the tail - where `part-2`, `whitepaper` and `slides` live - so truncate on word boundaries and always keep the last word. (3) A FORMAT WORD IS NOT AN IDENTITY. A reading list citing a paper as `[Whitepaper](...)` and its deck as `[Slides](...)` produced files called `whitepaper.md` and `slides.md`; a name that is only a file type should be rebuilt from the URL (and from the host when the URL says nothing either), and the rename reported rather than silently kept. (4) MATCH AGAINST EVERYTHING, THEN DECIDE WHAT MAY BE WRITTEN. Matching supplied files only against references that still lacked content re-homed a file whose own citation was already archived onto the next-best needy one, overwriting 50,091 bytes of the right document with 27,687 bytes of the wrong one. Separating "which reference is this" from "may it be written" also makes the honest outcomes reportable: already covered, and the reference a re-run moved a file AWAY from, which is now holding a document that is not it. - Two rules fell out that generalise past this tool: a file name is evidence and content must be able to veto it (two conversions saved under one blog post's title were the post and the whitepaper it describes, 39,962 and 126,742 characters with 2% of their text in common, and the split-off document had to be matched on its own first page because its name described its sibling), and a hand-obtained document must be STICKY against re-acquisition, because re-running the automated route can only replace it with the failure that made the import necessary.
- 2026-08-04 - CLASSIFYING WHAT AN ARCHIVED SOURCE IS WORTH NEEDS THREE CLASSES AND ONE RULE THAT IS NOT ABOUT LENGTH. A corpus of cited sources is not all research: alongside technique write-ups sit CVE database rows, vendor advisories, release notes, package registry pages, and pages that POINT at research published elsewhere. Length was the only signal, so an 11,032-character CVE entry outranked a 1,600-character payload README. Two rules fix it and neither counts words alone. (1) A RECORD-SHAPED URL IS A RECORD HOWEVER LONG IT IS - the length of a database row is scoring, references and boilerplate - and the URL patterns must be TIGHT, because a loose `support.*.com` or `/kb/` swallowed a PortSwigger knowledge-base article that is real research, and a research team's advisory host has to be exempted from its own path pattern. (2) A PAGE THAT POINTS AT RESEARCH RATHER THAN CARRYING IT is a record: no fenced code block, under 400 words of prose, and a link every few hundred characters, all three together. Code beats length in both, because a short README with two payload listings is worth more than a long press release. (3) TWO CATEGORIES MUST NOT BE RULES AT ALL - "this restates a source we already have" and "this is a tool's usage page" - because neither is safely detectable: a technique-term count scored a real TemplateParser exploitation article at zero, and a tool README is often the only description of the technique that exists. Shortlist those by weak signal WITH the evidence, and let a human decide. (4) A HUMAN'S DECISION LIVES IN THE HAND-EDITED POLICY FILE, NEVER IN GENERATED STATE, is read BEFORE anything is fetched (so "we keep no document for this" costs no request), and no rule may overwrite it. - The trap in (2) is that such a rule can hide a TRUNCATED extraction as "a short page", so before adopting it, the shortest documents it demotes were compared against the health probe's own measurement of their visible text: every one had kept 56% to 140%, which is what made them safe to demote.
- 2026-08-04 - AN ARCHIVE MUST RECORD WHY IT KEEPS NO DOCUMENT, OR IT REFETCHES THE SAME FAILURE FOREVER. Three causes look identical in a folder listing and are not the same thing: the capture is BROKEN (a browser TLS interstitial archived under the site's own citation and read as a 7,560-character document, an anti-scraper wall, a page whose whole body was its consent banner - all fixable, so they stay on the work list), the URL was never a citation (harvested from this repository's own tooling, including the archive's own configuration file), or a human judged it to add nothing. Detecting the consent case is DENSITY, not length: the archived banner runs 6.89 consent words per 1,000 characters and a real article carrying a cookie line runs 0.38, while a length test would have deleted real articles. - Two adjacent defects came out of the same work and generalise: a reference whose last acquisition FAILED still claimed the file an earlier successful run had written, and because the index already refused to list it, nothing linked to it and nothing swept it - so "which entries claim a file" and "which entries are listed" must be ONE rule; and an imported file that is a list of links must be refused, because a blog's index page shares its site title with every article on that site and therefore matches those citations almost perfectly by name.
- 2026-08-04 - WHEN A PAGE IS A JAVASCRIPT SHELL, LOOK FOR ITS API BEFORE REACHING FOR A BROWSER. GitHub security advisories, source files and issue threads were reaching the extractor as 139 to 264 characters and failing the content floor, which is correct behaviour on a document that genuinely is not in that HTML. All three are served in full by a documented public JSON API with no credentials: the advisory endpoint returns summary, whole description, severity, CVE, affected packages and references, `raw.githubusercontent.com` returns a cited file exactly (159,762 characters of real source in place of 150 characters of page furniture), and the issues endpoint returns the body and comments. Asking the global advisory database first also answers for repository-scoped advisories, so one endpoint covers both spellings of the same page. Discussions are the exception, GraphQL only. - Three rules came with it. (1) NEVER SEND A TOKEN, and never read one from the environment: an archive run must behave the same for every contributor, and a tool that quietly used one person's credentials produces results nobody else can reproduce. The price is the unauthenticated limit of 60 requests an hour, which a corpus with a couple of dozen such links never reaches. (2) REPORT A RATE LIMIT AS A REFUSAL, never as "this page has no content" - that difference decides whether a human retries or goes looking for another source. (3) A ROUTE THAT RETURNS THE WHOLE RECORD OR REFUSES MAKES ITS SHORT ANSWERS RECORDS, NOT STUBS - the same is true of a repository clone and of a hand-imported document - and without that distinction eight finished references sat on the list of things still to be fetched, one of them a 223,998-character whitepaper. Also: match URL rules on the DECODED path for readability, but re-encode before requesting, because a repository really does contain a file with a space in its name and a literal space in the request line is not a request.
- 2026-08-04 - A BROWSER LADDER MUST CHECK WHAT IT RENDERED, AND ITS SCOPE MUST BE KEYED ON WHY ACQUISITION FAILED. Two lessons that cost a lot of chasing. (1) A RENDERED WALL IS NOT A RENDERED PAGE: two rows were recorded as "confirmed alive by the browser ladder" while what was captured was a 264-byte edge-network "403 Forbidden" and a 2,245-byte anti-scraper challenge, and both then failed extraction three steps later with a health status of `ok` in between. Check the rendered DOM for refusal wording and ESCALATE to the next rung instead of returning it - one of the two cleared on the visible rung after headless was refused, which is exactly what a rung ladder is for - and report a refusal on every rung as unconfirmed rather than storing it. (2) SCOPE THE LADDER ON THE ACQUISITION REASON, not on a status: running it only for rows marked "needs a browser" missed every page that had already been given a DOM once and still came up short, and every page whose body turned out to be its consent gate. Keying on reasons that mean "the bytes we have do not hold the document" found nine more, all readable. Key on the reason rather than the outcome, or a row that failed with `http 404` gets sent to a browser to reproduce its 404. - Two more rules from the same pass. CODE IS EVIDENCE THE DOCUMENT WAS FOUND: a question-and-answer page is 20% article and 80% sidebar, so a loss guard measuring share-of-page called a good extraction a loss (4,045 characters carrying all three code blocks out of 19,983); letting two fenced blocks clear the ratio is the same "code beats length" rule the grading uses, one step earlier. And A FIELD THAT CAN BE CLEARED MUST MIRROR THE RECORD RATHER THAN BE COPIED WHEN NON-EMPTY: three documents kept a "content is missing" note after the run that disproved it, because an empty value never overwrote the stale one.
- 2026-08-04 - SOME PLATFORMS CANNOT BE READ AT ALL NOW, AND THE HONEST MOVE IS TO SAY WHICH ROUTES WERE TRIED. YouTube timed text was measured dead by three independent routes on the same videos: a plain fetch gets http 404 or a zero-byte body; the identical fetch made BY the page, with its own session and origin, also gets a zero-byte body; and clicking the page's own "Show transcript" opens a panel that never stops spinning. The caption URL now needs a token the real player generates, so this is a wall and not a bug to fix locally. Record the three attempts in the failure reason rather than a bare "no transcript" - otherwise the next person spends the same afternoon rediscovering it - and keep the browser route in place, because it is correct and costs nothing if the platform changes. The same applies to a proof-of-work wall and to a site whose TLS certificate has expired: report the exact reason, and do not reach for an accept-all certificate callback to make the number go down.
- 2026-08-04 - THE ROUTE THAT STILL WORKS FOR A YOUTUBE TRANSCRIPT IS `yt-dlp`, AND IT BELONGS IN A CONTAINER. Every route a hand-written client owns is refused: a plain fetch of the caption URL gets http 404 or a zero-byte body, the identical fetch made BY the page with its own session and origin also gets a zero-byte body, and the page's own "Show transcript" opens a panel that never stops spinning, because the URL now needs a token the real player generates. `yt-dlp` asks a different player client that still answers, and it recovered 12 of 13 talks at 17,146 to 45,316 characters each, including human-made tracks. `--skip-download --write-subs --write-auto-subs --sub-langs 'en.*' --sub-format json3` fetches the captions and never the media. Two operational notes: the library alternative (`youtube-transcript-api`) is blocked on cloud-provider address ranges and fine from a residential one, and both tools break whenever the platform changes, so pin the version and expect to bump it as a visible edit. - RUN IT IN A CONTAINER, and treat that as a property to protect rather than a precaution to remember: this is the only third-party code such a tool executes, it is large and fast-moving, and its whole job is parsing hostile input. Give it one throwaway output directory and the network; do NOT give it the repository, the content store, the environment, any capability, a writable root filesystem or a root user, and bound its memory and process count. Pin the base image by DIGEST and the tool by version so a rebuild cannot become a different image, and assert those properties in tests so loosening the sandbox has to change one. Absent runtime is a clear SKIP with a reason, never a failed run. On Windows a POSIX-style path from a Git Bash shell reaches Docker as `C:/Program Files/Git/out` and the run dies on an "invalid working directory", so hand it the native path.
- 2026-08-04 - ONE CONTAINER AS THE SANDBOX FOR EVERY UNSAFE COLLECTION JOB, not one per tool. Two different things belong in it and they share a boundary rather than a category: third-party code that would otherwise run on the host (a caption downloader, a PDF rasteriser - both large C or fast-moving parsers fed documents somebody else chose), and a fetch that deliberately relaxes something the in-process client must never relax. Putting the certificate exception in the container rather than in the fetcher is what lets "our client always verifies" stay TRUE: the exception is a different process behind a boundary nothing reaches by accident, and what comes back is bytes that go through the same extraction as any other fetch. Pass the relaxing flag at the CALL SITE, never in the shared argument list, so no other route can inherit it, and make the command refuse to run as a sweep - name the one reference. Assert the container's properties in tests so loosening the sandbox has to change one.
- 2026-08-04 - NOT EVERY WAYBACK CAPTURE OF A URL IS THE SAME PAGE, and the replay is not the capture. A citation pinned to whichever capture was found first can be pinned to a 9,046-byte copy of the site's own "404" while a 380,504-byte capture of the same URL is the actual PDF, or to a 5,775-byte JavaScript shell while an older capture carries the whole article. Ask the CDX index what else exists and prefer the LARGEST successful capture. Use the `id_` replay form (`/web/<timestamp>id_/<url>`), which returns the original bytes instead of the archive's rendering with its toolbar and rewritten script - and which is the only form in which a captured PDF is still a PDF. THE CDX LENGTH IS A COMPRESSED RECORD SIZE and cannot be compared against uncompressed bytes already held: a capture listed at 19,564 was 140,067 bytes when fetched, and rejecting it as "no bigger than what we have" threw away the only copy with the article. Compare candidates only with each other, then fetch and compare like with like. A capture also SUPERSEDES a stored browser render, because sometimes the wall is what the browser captured.
- 2026-08-04 - WHEN A PDF'S TEXT LAYER IS UNREADABLE, RENDER THE PAGES AND HAVE THEM READ - and keep that a two-step route on purpose. `pdftoppm -png -r 150` in the container turns each page into a legible image; a reader, human or model, then writes what the pages say and that goes back through the ordinary import path. Deciding what a page SAYS is not a converter's job: the converter that guessed produced text with 32% of its words containing no vowel, which is worse than nothing because it reads as though somebody checked it. Tell the reader to write only what is on the page. - Three stale-state defects came out of this work and they are one shape: a FAILED attempt must not overwrite bytes already held (a 126,805-byte capture was replaced by the 2,245-byte wall the failing attempt read), a better source must supersede an older stored one rather than losing to it by preference order, and recovering a document must RELEASE the identity minted from the broken capture - slug, publisher, and the health record whose `final_url` was still attributing a Chinese advisory to the browser's own `chromewebdata` scheme.
- 2026-08-04 - A FETCH CAP SIZED FOR A PROBE SILENTLY TRUNCATES EVERY DOCUMENT IT IS APPLIED TO, and a truncated PDF is invisible to every ordinary check. Seven were stored at exactly the cap - 2,097,152 bytes - each still starting with `%PDF-`, each yielding real text for the pages before the cut and glyph soup after it; one was 12% of a 16,773,574-byte conference deck. Three things are needed together, because any one alone leaves the trap open: give a document fetch a document-sized cap, REFUSE a PDF that does not end with `%%EOF` (that is the only cheap proof the download completed), and on a failed attempt keep the MORE COMPLETE bytes rather than the newest or the oldest - "newest" loses a good capture to the wall a failing attempt just read, and "never replace" keeps the truncated file instead of the whole one the next attempt downloaded. The exact-power-of-two size is the tell; look for it whenever extracted text degrades partway through a document.
- 2026-08-04 - MEASURE DOCUMENT DAMAGE PER PAGE, AND NOT WITH EVERY SIGNAL YOU HAVE. A whole-document quality gate averages a broken page away: a deck with seven unreadable pages out of eight passed it, because the eighth carried enough prose to lift the mean. Damage in a PDF is per page by nature - one font with no usable encoding map, one stream that decoded into font data - so measure each page and REPORT THE PAGE NUMBERS, which is what makes a repair targetable rather than a whole-document re-do. But use only the signals that survive page scale: a replacement-character ratio and a letters-or-spaces ratio work, while a "share of words containing a vowel" test does not, because a PDF routinely emits a title slide with no spaces between text runs ("ProxyLogonis Just the Tip of the IcebergA New Attack Surface") which is perfectly readable and has almost no word-shaped runs in it - judging pages on it called 46 readable title slides damaged. - When a document's fonts genuinely carry no usable encoding map, no text extractor will ever read it: render the pages to images in the container and have a reader write what they say, keeping that a deliberate TWO-STEP route. Deciding what a page says is not a converter's job, and the converter that guessed produced text with 32% of its words containing no vowel, which is worse than nothing because it reads as though somebody checked it.
- 2026-08-04 - A TRANSIENT FAILURE MUST NEVER DESTROY A DOCUMENT ALREADY HELD, and the trap is two steps away from where it looks. An unauthenticated API allows 60 requests an hour; running a corpus pass several times hit the limit, ten references "failed", and the NEXT command - an index run with an orphan sweep - deleted all ten files, every one of which had a good slug, grade and stored content. The same failure branch also ran for a SKIPPED hand-import, so 18 imported documents lost their grade too. Three rules fix it and all three are worth keeping. (1) WITHDRAW A DOCUMENT ONLY WHEN A RULE REFUSED IT (a broken capture, a consent gate) - that is the only case where what is held is known to be wrong; a fetch that merely failed is not evidence about the copy on disk. (2) A ROUTE THAT DEPENDS ON A REMOTE SERVICE SHOULD RE-RENDER FROM STORED CONTENT when the service refuses, which costs no request and keeps the archive whole. (3) "A FILE SHOULD EXIST" MUST BE ONE RULE shared by whatever lists files and whatever sweeps them, keyed on what the entry HOLDS rather than on the last step's outcome - two rules drift, and the drift is invisible because the folder still looks full.
- 2026-08-04 - SWEEP GENERATED OUTPUT FOR MALFORMATION, BUT ONLY SHIP THE CHECKS YOU HAVE VERIFIED AGAINST THE FILES THEY FLAG. Four real defects came out of one sweep of 503 files: a gzip body the client never unwrapped and decoded as text (2,977 replacement characters in 6,230 - decide on the MAGIC BYTES, because the header is what lied), HTML entities written verbatim because the parser unescapes once and the page had escaped twice, site markup reaching the text as literal tags for the same reason (a `<span>` with an attribute is never content, while `<string>` and `<int>` are the subject matter and must survive), and a document destroyed by a transient failure. Equally important, five of the sweep's nine categories were the CHECK being wrong: 138 "ends mid-sentence" hits that were all page footers, an inline ```span``` counted as an unbalanced fence, a `c#` language tag falling outside a character class so eight balanced files read as unclosed, `\n` inside quoted code read as a raw escape, and XML payload elements read as leftover HTML. Ship the three that survived scrutiny and drop the rest: a rule that cries wolf gets switched off rather than fixed, which costs the checks that were right.
- 2026-08-04 - PUBLISHER FURNITURE THAT SITS IN THE ARTICLE'S OWN FLOW NEEDS A TEXT-LEVEL TRIM, and the patterns must be COUNTED rather than imagined. Container-level chrome removal catches a `<footer>` or a `class="newsletter"`; it cannot catch a call to action with no class worth naming, and 111 of 503 archived documents ended with one - about 21,000 characters of "Ready to engage / Get in touch / Copyright", vendor panels, "Press enter or click to view image in full size", "Back to all", "Author Posts". Derive the rules by counting the trailing blocks of the whole corpus, which also produces the list of things that must SURVIVE (`## References` in 20 files, `## See also`, `## Conclusion`, `### Disclosure timeline`, `### Credit`) - and none of those is a guess either. Four safety rules make it safe to run: trim INWARD FROM THE EDGES and stop at the first block that is not furniture (so an advert mid-article stays, which is the price of not guessing), never treat a block holding a fenced code block as furniture, never treat a long block as furniture because calls to action are short, and never let a trim take a large share of the document. Record every removal. - The rule that nearly cost real content: "a block that is only an image" deleted 2,115 characters of a conference deck, because ON A SLIDE HOST EVERY SLIDE IS AN IMAGE WHOSE ALT TEXT IS THE SLIDE. Only an image with an EMPTY alt is decorative.
- 2026-08-04 - TRANSLATING AN ARCHIVED SECURITY DOCUMENT MEANS MASKING THE PAYLOAD FIRST. Such a document is made of type names, method names, CVE identifiers, base64 blobs, XML and shell commands, and every one of them IS the research: a translated `System.Windows.Data` is not a smaller mistake than a mistranslated sentence, it is a corrupted gadget. So replace every non-prose construct with a placeholder before showing the text to any translator - fenced blocks first so an inline rule cannot shred them, then inline code, links, URLs, dotted identifiers, CVE ids, hashes, tables - and restore them byte-identically afterwards. Protect the placeholder SHAPE itself, or a document that already contains one collides with yours. A placeholder that does not come back is a REFUSAL, not a warning. Keep the original in the rendered file with the translation above it: a machine translation of a security write-up is evidence ABOUT the original rather than a replacement for it, and a reader must be able to check it. - Two measurement traps in deciding WHAT needs translating: count words on the MASKED text, because on the raw text `.com` fired a Portuguese stop-word rule 67 times on an English page and "Las Vegas" fired the Spanish one 120 times on an English deck; and match a declared language by its PRIMARY SUBTAG, because listing `en`, `en-us`, `en-gb` exhaustively queued a Singapore write-up tagged `en-sg` for translation.
- 2026-08-04 - A DECLARED `en` IS NOT EVIDENCE OF ENGLISH, AND A PAGE'S OWN LANGUAGE TAG IS TRUSTWORTHY IN ONE DIRECTION ONLY. A blogging platform sets `lang` once for the whole site: Medium serves every post as `lang="en"`, so Vietnamese, Chinese and Japanese write-ups on it declared English and sat in the archive untranslated while the backlog reported itself clean. Believe a declared FOREIGN language (nobody sets that by accident) and make a claim of English survive the measurement. - JUDGE A DOCUMENT FOREIGN ONLY ON POSITIVE EVIDENCE OF ANOTHER LANGUAGE - a non-Latin script, or that language's own stop words. "Few English function words" feels like the general test that avoids needing a word list per language, and it is wrong: slides, code listings and reference pages are made of fragments rather than sentences, so a conference deck scored 0.012 and a Microsoft design document 0.052 on that measure, the same range as a Vietnamese write-up. Using it flagged four plainly English documents for translation. Use the English-word share only to confirm that a SHORT segment IS English, never to conclude that a document is not. - Calibrate the foreign-word threshold against the whole corpus and drop every stop word that collides with the subject matter: `com` is Portuguese and fired 226 times across 22 English documents because this field is full of COM, the Component Object Model, and `des`, `con`, `del`, `las`, `los`, `sur`, `les`, `est` all fire on English prose and place names ("Las Vegas" is in half the conference decks). With those removed the genuinely foreign documents scored 0.026 and up and the English ones at most 0.0065, so the threshold goes in that gap - one collision is worth more than a thin margin, because its cost is a whole English document queued for translation. - Decide per SEGMENT, not per document. A document is rarely uniformly one language (a Chinese write-up quotes English error messages, an English one carries a stray Chinese paragraph, a repository README is mostly English around the part that is not), and re-translating a sentence that is already English is a chance to alter something nobody asked to change. Hand over only the foreign segments, keep the FULL segment map, and rebuild from it - so an untouched segment returns verbatim and a translator that drops one cannot silently delete a paragraph. A segment too short to measure inherits the document's verdict, because a two-word heading in a Japanese article is Japanese. - And decide a SEGMENT on presence, not share: a document is classified by what most of it is, but a segment is a unit of work, so any foreign text in it is text somebody has to translate. Judging segments by share left the Chinese cells inside a large mostly-English table untranslated, and the Chinese titles in a list of otherwise English links, because each block averaged out as English. - "Not Latin" is NOT "another language", and the difference matters as soon as presence is the test: asking only whether a character is outside the Latin script queued three documents on the strength of a Greek sigma in `σ∈State`, a stray hieroglyph, and a PDF whose text layer had decoded to mojibake. Name the writing systems that actually mean a human wrote in another language (CJK, Hangul, Cyrillic, Hebrew, Arabic, Devanagari, Thai) and leave Greek out, because in a .NET corpus it is mathematics.
- 2026-08-04 - A TITLE IS CONTENT AND AN AUTHOR IS AN IDENTIFIER, so translate the first and never the second. Maintainer decision: a file headed in a script the reader cannot read tells them nothing about whether it is worth opening, and the heading is the thing people scan a folder by, so the document title and the publisher get translated with the body. An author does not: "Ivan1ee dotNet security matrix" is a credit that matches nothing searchable. - Store the translation BESIDE the original rather than over it and let the two surfaces differ: the visible heading uses the English title, while the frontmatter title, the attribution line and the citation block keep the source's own spelling, because that is what a citation has to match. - Two mechanical traps. Metadata masked separately from the body needs to share ONE placeholder numbering, or the two sets collide and restoring one corrupts the other (pass the existing map in rather than starting a new one). And metadata segments must be excluded when the body is rebuilt, exactly like lifted code comments, or the title is joined into the article text.
- 2026-08-04 - A CITED WAYBACK CAPTURE IS A CHOICE SOMEBODY MADE, AND IT CAN BE THE WRONG ONE. A reading list can pin a replay URL whose capture is a bot wall rather than the page: one cited a 2024 capture that extracts to 99 characters of slider CAPTCHA, while 2019 and 2022 captures of the same URL carry the article. So when a capture fails, WALK the other captures instead of giving up on the cited one - largest first, ties oldest first, because a site gets its content before it gets its anti-scraper - and check each fetched capture for wall wording before accepting it. The archive tool must fix this on its own side: it may never edit the reading list. - The same run re-proved the rule that a rate-limited lookup is not an empty index. The CDX helper swallowed every failure into `[]`, so a 429 printed "no better capture exists" - a statement about the source - and the reference read as dead. Raise on "could not ask" and report it apart from "nothing to find"; the first run said none, the retry found a capture 2.2x larger.
- 2026-08-04 - A TITLE READ OFF A BOT WALL IS NOT A TITLE, and it propagates. The probe records what the page called itself, so a portal that answered with a bot check filed a KTH doctoral thesis as "Making sure you're not a bot!" - heading, frontmatter, file name and slug alike. Two consequences worth knowing: filename-based import matching can never work for such a reference (no word in common between `thesis-Mikhail-2024.pdf` and the wall's words), so a maintainer needs a way to STATE which URL a hand-obtained file is, and that statement must outrank every heuristic rather than compete with it. And a corrected title has to release the pinned slug, because the file name is the part a reader sees first - the usual "a slug is pinned once it exists" rule is about avoiding churn, not about preserving a mistake. - THE WIDER RULE, hit twice in one session: a maintainer's recorded judgement has to reach EVERY path that can act on it, and the hand-import path is the one that gets forgotten. The classifier had honoured an override from the start, but the import call never passed one, so a decision written for a hand-obtained page was silently ignored and a rule re-graded it on every run. That path is exactly where judgement matters most, because those are the pages no automated route could read.
- 2026-08-04 - IN A PDF, THE WORD SPACES CAN BE NUMBERS RATHER THAN CHARACTERS. A `TJ` array interleaves strings with horizontal adjustments in thousandths of an em, and plenty of typesetters - TeX above all - never emit a space character at all, drawing every word gap with one of those numbers. An extractor that keeps the literals and drops the numbers produces text that passes every per-character quality check and is still unreadable: a 566,247-character thesis came out with 951 spaces in it, as `Code-ReuseAttacksinManagedProgramming`. Treat an adjustment beyond about 140 as a word break and the rate goes from 0.002 spaces per letter to 0.167 (English prose is ~0.20). - The neighbouring trap: do NOT reach for the document's /ToUnicode map to "improve" text that already reads. Read per document rather than per font, it applies one subset font's table to another's codes - on this thesis it turned every `n` into a quaver and `W` into omega. It is a repair for text that is already nonsense, and any attempt to prefer it needs a measurement showing it reads better, not an assumption that the document's own map must be right.
- 2026-08-04 - WHEN A PIPELINE STEP REGENERATES ITS INPUTS, KEY THE EXPENSIVE OUTPUT BY CONTENT SO A RULE CHANGE COSTS ONLY WHAT ACTUALLY CHANGED. Re-preparing a translation deletes every chunk file including the finished translations, which is correct - segment numbering comes from the masking, so applying an old translation to a new preparation is silent corruption rather than lost work. But a chunk whose text comes back BYTE-IDENTICAL is the same work: keep its translation, matched on the chunk's own content. Without that, a change that appends one segment per document re-translated an entire corpus three times over.
- 2026-08-04 - A PIPELINE STAGE THAT NOTHING FAILS WITHOUT IS THE ONE THAT GETS SKIPPED, so give it a gate. Fetching, classifying and rendering a foreign-language document all succeed on their own and produce a file with frontmatter, attribution and content - it looks finished, and only a reader who cannot read the content ever finds out. The offline verifier now asks "is any document not in English and missing a translation" on every run, which turns a step people forget into a warning they have to clear. - The same run exposed the cost of a SILENT FALLBACK: the content store falls back to a workspace cache when its environment variable is unset, and every count came out quietly wrong (a translation backlog of 36 reported itself as 11, because entries whose content the cache lacked were skipped rather than counted). A tool that cannot see part of its input must say so, never report the visible part as the whole.
- 2026-08-04 - WHEN MASKING CODE BEFORE TRANSLATION, MASK ONLY CODE. Everything a human wrote to be READ is prose even when it sits inside punctuation, and masking the whole construct is the easy mistake: protecting `[text](url)` whole, and table rows whole, left 2,064 Chinese characters untranslated inside documents that reported themselves fully translated. - 2026-08-05 - WHEN A CALLER NAMES THE OUTPUT, A TOOL MUST NOT TAKE THE INPUT FROM AMBIENT CONFIG. A query CLI that caches an expensive source file into a derived index re-checked freshness by comparing the index the caller had NAMED on the command line against a source path it had picked up from an environment variable. The two described different corpora, so the size and timestamp differed, so it declared the index stale and rebuilt it - silently replacing a just-built index with a completely different body of code. The failure is not a wrong answer, it is DATA LOSS, and it survives every "always pass the explicit flag" habit, because the explicit flag WAS passed; the implicit half is what was wrong. Three rules follow. An implicit default may only fill in a value the caller left out, and never one that changes the meaning of a value the caller supplied. - 2026-08-05 - A PUBLISHED-LITERATURE ARCHIVE AND A CODE-GRAPH SWEEP ANSWER DIFFERENT QUESTIONS, so mining the archive for missing FRAMEWORK gadgets is the least productive thing to do with it. Reviewing the whole reference archive against the tool's own source produced 291 in-box type names not mentioned anywhere in it; deduping that against the code-graph frontier already recorded in the private working area removed exactly the top of the list, because a sweep reads every type while an article names only the ones somebody chose to write up. - 2026-08-06 - A FILE LITERALLY NAMED `NUL` AT THE REPO ROOT IS A `2>NUL` REDIRECT RUN IN THE WRONG SHELL. `NUL` is the null device in cmd.exe only; in PowerShell and in bash it is an ordinary file name, so `<command> 2>NUL` creates a real file holding whatever went to stderr (this one held a single WSL startup error). - 2026-08-09 - A LEAKED LOCAL PATH IS NEVER SPELLED THE WAY YOU SEARCH FOR IT, so a fixed-string scan for the developer's own path reports clean while the path sits in the file. - 2026-08-09 - IN A LEAK SCAN, EVERY SILENT FAILURE READS AS "CLEAN", so the plumbing needs as much suspicion as the rules.
