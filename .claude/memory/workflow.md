# Workflow

Git and multi-agent working conventions. Entry format: `date - what - why`.

- 2026-07-28 - NEVER BLOCK ON A LOCKED `bin\Debug\ysonet.exe` - BUILD A SECOND COPY UNDER ANOTHER PATH AND TEST THAT. The maintainer often has an interactive `ysonet.exe` open while asking for changes, and msbuild then fails the COPY step (`MSB3027`/`MSB3021`, "the file is locked by: YSoNet (<pid>)") while still compiling successfully to `obj\`. That failure mode is the dangerous one: the solution build reports errors but `ysonet.Tests.exe` still RUNS - against the STALE binary - so the suite goes green and proves nothing about the change. Check `Get-Process ysonet` before believing a pass after a copy error. The fix is one command, no waiting and no asking them to close anything:
  `msbuild ysonet\ysonet.csproj -p:Configuration=Debug -p:OutputPath=<scratch dir> -p:RunYsonetTests=false`
  which produces a complete, runnable `ysonet.exe` plus its dependencies in the scratch directory, enough to compile-check and to smoke real CLI behaviour (generation, `--help`, `-t`, the DoS harness, which takes the exe path as an argument). Only the in-process `ysonet.Tests.exe` run still needs the real `bin\Debug`, so ask for the binary only when the full suite is genuinely the next step. - Waiting on the maintainer to close a window is pure delay, and the alternative (running the suite anyway) is worse than delay because it reports a pass that measured nothing.

- 2026-07-27 - RULE for working a `dev-kitchen/todo/*.md` item: FIX every issue you find while working it, in the same change, instead of spawning a new todo file for the leftovers. Filing a follow-up file is what the maintainer does not want: the point of picking the item up is to finish it. If any part of the item is vague (which option, how far the scope reaches, whether a related branch counts), ASK the maintainer, and keep asking after each answer until nothing is left ambiguous. When the work is complete and verified, ASK for approval to delete the todo file, then delete it and drop its row from `dev-kitchen/todo/README.md`. - The escaping sweep is the case that produced this rule: the todo said `ObjectDataProvider` was "a different path, not reviewed here", and reviewing it turned up a REAL fastJSON corruption of exactly the same kind. A new todo file would have parked a live bug that the sweep was supposed to close.
- 2026-07-22 - When starting new or parallel work that will live on its own branch, give the agent an isolated checkout with a git worktree (`git worktree add ../ysonet-<topic> master`, then work on a branch inside it) instead of sharing the one repo checkout. At minimum, use a dedicated branch. - Two agents sharing a single working tree block each other: you cannot switch off or delete the branch that is checked out, and switching branches reverts and clobbers the other agent's uncommitted work-in-progress. A separate worktree gives each agent its own working directory, so branches can be created, switched, and deleted freely without ever touching the other agent's files. This came up when a branch could not be deleted because a second agent was mid-edit in the same checkout.
