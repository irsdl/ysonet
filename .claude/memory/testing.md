# Testing (ysonet.Tests)

- 2026-07-26 - A gadget whose payload names a DLL for the TARGET to load can be fired for real
  without compiling anything: make the already-built `ysonet.Tests` assembly BE that DLL.
  `ysonet.Tests/InstallerFixture.cs` declares a public `[RunInstaller(true)]`
  `System.Configuration.Install.Installer` whose constructor appends one line to a marker named
  by the `YSONET_INSTALLER_MARKER` environment variable, which only the tests set, so the class
  is inert in every other context. `FireAssemblyInstallerLoad` points the payload at
  `typeof(YsonetTestInstaller).Assembly.CodeBase` and asserts the marker holds exactly ONE line.
  Two things this buys: the effect is synchronous (no spawned process, so no `MarkerWaitMs`
  polling), and the LINE COUNT is the real assertion - `AssemblyInstaller` sets a private
  `initialized` flag after the first `InitializeFromAssembly`, so a ComboBox carrier that reads
  `HelpText` several times must still construct the operator's installer once. Needed
  `System.Configuration.Install` and `System.Windows.Forms` references in `ysonet.Tests.csproj`.
  Note the assembly is an `.exe`, which is why the gadget accepts a managed `.exe` as well as a
  `.dll` (`Assembly.LoadFrom` takes either) and rejects a bare program name instead. - The
  documented alternative was to compile an installer at test time, which is exactly the
  antivirus-wedged `csc` path that already makes the compile-based gadget tests flaky.

- 2026-07-26 - A UI test must reach a module by NAME, never by POSITION. `AllMenusRender`
  drove the plugin menu with `Digit(2).Up().Enter()` and asserted `ViewState Settings`,
  which silently meant "ViewState is the last plugin"; adding the `Xps` plugin (which sorts
  after it) failed the test with no bug anywhere in the product. Both that assertion and the
  `YSONET_DUMPUI` dump now use `Digit(2).Type("ViewState").Enter()`, the same type-to-filter
  the gadget tests already use. - The failure looks like a rendering regression and costs
  time to trace back to alphabetical order; any new plugin or gadget can trip a positional
  keypress.

- 2026-07-26 - A per-process FRAMEWORK MITIGATION switch can be flipped by reflection, which
  makes "patched blocks it / unpatched runs it" a single testable pair with no machine
  change. The CVE-2020-0605 XPS fix is gated by an internal static settable property named
  `DisableLegacyDangerousXamlDeserializationMode` on TWO classes -
  `System.Windows.ReachCompatibilityPreferences` (ReachFramework, gates the `.fdseq`) and
  `System.Windows.FrameworkCompatibilityPreferences` (PresentationFramework, gates
  `.fdoc`/`.fpage` through `XpsValidatingLoader`) - both defaulting to restricted.
  `SerializersHelper.Xps_set_legacy_dangerous_mode` / `_restore_` / `_get_legacy_switch_state`
  wrap them, and `FireXpsDocument` asserts the blocked half FIRST (short wait, it is an
  absence), then the fired half, then VERIFIES the restore, because the switches are
  process-wide statics and `ClipboardPayloadsTrigger` depends on the default. Read the
  property before writing it: that forces the static constructor to apply the app.config or
  HKCU value, so the captured "previous" is the real one. - Without the restore check, one
  flipped switch quietly changes every later XAML/XPS load in the same run, and the test
  that notices is a different one.

- 2026-07-26 - Clean up a fire marker with the shared `SafeDelete`, never a bare `File.Delete`. `WaitForFile` returns the moment the file EXISTS, and `cmd /c echo x > marker` creates it before it writes and closes, so a delete straight after the wait can land while the spawned `cmd` still holds the handle and throws "The process cannot access the file ... because it is being used by another process". That surfaces as an INTERMITTENT failure of an unrelated-looking test (seen once as `Bridged gadget chains (--bgc) generate for every consumer`, passing on the runs either side of it), because the throw comes from the `finally`, not from any assertion. Four cleanups still used a bare delete and were switched; the startup sweep is the intended backstop for a marker that outlives its test. - A cleanup path must never be able to fail a test, and this one failure mode reads as a payload problem when it is pure housekeeping.

- 2026-07-26 - A FINALIZER effect is testable deterministically, and the weak reference is what makes it evidence rather than a guess: deserialize inside a `[MethodImpl(MethodImplOptions.NoInlining)]` helper that returns ONLY a `WeakReference`, then `GC.Collect()` / `GC.WaitForPendingFinalizers()` / `GC.Collect()`, then assert the weak reference is DEAD before asserting the effect. Without the separate frame the caller's local keeps the object rooted and the cell looks like a payload that did not fire; without the dead-reference check a pass does not prove the finalizer ran. `FireTempFileCollectionDeletes` is the pattern - 20 cells (5 formatters x minify x {finalizer, explicit `Dispose`}), each with a SENTINEL file beside the target that must survive, which is what proves the payload deleted only what it was given. The explicit-`Dispose` half is worth firing separately: it is the deterministic path and it also suppresses the finalizer, so nothing is left queued. Any test that reconstructs a finalizable target type for INSPECTION must `GC.SuppressFinalize(obj)` in a `finally` (see `WithDeserializedTempFileCollection`), or the runner itself ends up holding an armed object. - Before this the plan for the gadget assumed the effect could only be "forced" and not attributed.

- 2026-07-25 - An outbound SMB/UNC callback IS testable without binding port 445: watch for the DNS lookup that must precede the connection - Windows resolves the host name before it opens the SMB session, so a recorded DNS query for a run-unique name proves the callback was attempted even when outbound 445 is blocked. That is the whole reason the OOB tier exists (`--oob` / `YSONET_OOB_TESTS`, `OobSession` in `ysonet.Tests/Oob.cs`, `interactsh-client` from `tools/interactsh/`). Measured on 2026-07-25 with `Path.GetFullPath`: `\\<label>.<oob-domain>\share\aaaaaa~1\x` blocked for 5.0s and produced DNS A/AAAA queries, while the same host without a `~` component returned in 0ms and produced nothing - so the control case is what makes the positive result mean "short-name expansion", not "something resolved the name". Two more traps: resolvers randomise the case of the query name (DNS 0x20), so `full-id` comes back as `tILDe.d9IJ8...` and label matching MUST be case-insensitive; and the bare payload domain gets its own interactions from the client's own keep-alive, so match the LABEL, never just the correlation id. - Before this, the FileSystemInfo plan was blocked on "provision a test-owned SMB endpoint", which no developer workstation can offer.

- 2026-07-25 - To decide whether a FULL-tier failure is yours, run the suite in a clean `git worktree` at HEAD instead of reasoning about the diff - `git worktree add <tmp> HEAD --detach`, copy `packages/` into it, build Debug, run `ysonet.Tests.exe --full`. The worktree has its own `ysonet.sln` root, so `FindWorkspaceRoot()` sends its test artifacts to a separate `temp/`, and the two suites cannot fight over marker files. Measured on 2026-07-25: HEAD 153 passed / 4 failed vs the working tree 181 passed / 2 failed, which settled in one run that three deterministic execution failures pre-dated all uncommitted work. - Cheaper and far more conclusive than reverting parts of a mixed working tree.
- 2026-07-26 - Not every runtime effect needs the marker/`WaitForFile` machinery: a payload whose sink is the DESERIALIZER itself (no spawned process) changes the file system synchronously, so the assertion goes right after the deserialize with no wall-clock budget at all. `FireFileOperations` in `PayloadsFireIntoTestSinks` is the pattern - 90 cells (5 operations x 3 formatters x 3 root containers x minify) each generate, `RunSTA(DeserializeAs(...))`, then assert the real file/directory state and `RuntimeBuild.RecordFired`. It still uses `RunSTA` because the confused comparer can throw AFTER the effect. Reserve `MarkerWaitMs` polling for the `cmd /c echo` family, where the marker really is written by another process. - The polling budget exists for process spawn latency; borrowing it for an in-process effect only makes a failing row slower to report.
- 2026-07-25 - "marker not created" was usually a LATE marker, not a dead payload, and the leftover files are how you prove it - every fire helper deletes its marker in `finally`, so a marker file still sitting in the artifact dir after a run means the spawned `cmd` wrote it AFTER the test gave up. One run reported 34 failures and left exactly 34 matching `ysonet_fire_*.txt` files. Fix was the shared `MarkerWaitMs` (15s) constant used by every POSITIVE fire wait, replacing the old 2000/2500/3000/3500 literals; `WaitForFile` polls every 100ms so a healthy row is just as fast, and the ceiling is only paid when a payload really does not fire. The negative clipboard case (`WpfXamlPayloadRuns(..., restrictive: true)`, which asserts ABSENCE) deliberately keeps its short bound. - Before blaming a gadget, list the artifact dir; a fixed wall-clock budget on a loaded machine is a false-negative generator.
- 2026-07-25 - Never read a crashing child process's pipes with a blocking `ReadToEnd()` - when the child fail-fasts, Windows Error Reporting inherits its stdout/stderr handles and holds them open, so the read never sees end of stream and the PARENT hangs forever (measured: 300s+ with no exit, while the same child run from a shell finished in under a second). Use the async drain the fire helpers use (`BeginOutputReadLine` + a handler) and wait on the PROCESS with a timeout, never on the streams. Same rule for `IsolatedSelfTest.Run`. Second-order effect worth knowing: a machine that has accumulated stuck `WerFault` processes reaps later crashes slowly, so a self-test that normally reports in 0.7s can take the whole timeout - check `Get-Process WerFault` before believing a slow result. - This is the difference between a 0.7s honest report and an apparent infinite hang, and it looks exactly like a bug in the payload.
- 2026-07-25 - Deserializing a TypeConfuseDelegate XAML wrapper (`GetXamlGadget`, so `ActivitySurrogateDisableTypeCheck` and `XamlAssemblyLoadFromFile` variant 1) IN-PROCESS kills the host: the CLR fail-fasts with 0xC0000409 inside `clr.dll` AFTER the XAML has already run, for every container including the shipped SortedSet default. `ysonet.exe -g ActivitySurrogateDisableTypeCheck -t` reproduces it standalone, and `RunSTA` cannot save you because the process never reaches a catch. Any test that fires this family must run in a SUBPROCESS and read the marker file, never the exit code - `FireSelfClosingCs` already did this for the `*FromFile` gadgets, and `XamlContainersEvadeSortedSetBinder` spawns the test exe itself through the hidden `YSONET_XAML_CONTAINER_PROBE` env var (same pattern as `YSONET_DUMPUI`). The TOOL now handles it too: those gadgets override `SelfTestNeedsChildProcess`, so `-t` runs in a child ysonet process (`Helpers/Core/IsolatedSelfTest.cs`) and ysonet itself survives with a one-line report. - A whole-runner crash looks like an msbuild "exited with code -1073740791", not like a failing test, so it costs a lot of time to trace back to one row.
- 2026-07-25 - `RunSTA` now prints the exception it swallows when `YSONET_TRACE` is set - it still swallows by default (most gadgets throw AFTER firing), but the trace turns a silent "marker not created" into a diagnosable event. An ABSENT `[sta-throw]` line is itself evidence: it means the payload deserialized cleanly and simply did not act, which is what exposed the ObjectDataProvider `IsInitialLoadEnabled` bug.
- 2026-07-25 - A "marker not created" fire failure is NOT proof the gadget is broken - check it standalone first: `ysonet.exe -g ObjectDataProvider -f Xaml --variant 1 -c "cmd /c echo x > <marker>" --rawcmd -t` creates the marker every time, while the same cell fails inside the FULL run. 157 of 158 cells fire in that same process, so the tail failures are in-process harness state/ordering or the 2500-3000ms `WaitForFile` budget after ~150 spawned processes, not the payload. Also ruled out on that machine: antivirus (`Get-MpComputerStatus` showed real-time protection OFF) and restrictive-XAML contamination (`-p Clipboard --mode wpfxaml --test` does a restrictive load then a normal load in one process, and the normal load still fires).

- 2026-07-25 - Denial-of-service gadgets are outside both test tiers and no test ever acknowledges one - `EveryGadgetGeneratesAPayload` and `GadgetFullMatrixGenerates` skip them from `DosPolicy.IsDosGadget` (facet-derived, never a name list), the three generic fire helpers route through `RefuseToFireDosGadget` and add a hard FAILURE if a DoS row appears (firing one would terminate the runner), and `DosGadgetsAreContained` proves the refusal, the `--bgc` precedence and the bulk exclusion without building anything. Building a DoS payload is a third opt-in gate, `ysonet.Tests.exe --dos` or `YSONET_DOS_TESTS`, which unlocks only the generation half of that one test. - A gate that tests have to satisfy would push people to acknowledge by default, which defeats the guardrail; skipping is the safe default.
- 2026-07-25 - A fake `IGenerator` for a test must live under a namespace containing `Helpers.TestingArena` (see `ysonet.Tests/DosFakes.cs`, namespace `ysonet.Tests.Helpers.TestingArena`) - `GadgetRegistry.GetAllGadgetTypes` filters on `AssemblyQualifiedName.Contains("Helpers.TestingArena")`, so that keeps the fake out of the catalogue, the help, the category search and every matrix. Without it the fake IS listed (the registry reflects over every loaded assembly, including ysonet.Tests) but cannot be instantiated, and `EveryGadgetGeneratesAPayload` fails on the null instance.

- 2026-07-25 - The test-artifact helpers now exist in `ysonet.Tests/Tests.cs` (region "Test artifact locations", next to `MakeTempFile`): `WriteTestArtifact(name, content)` for a file the test writes, `TestArtifactPath(name)` for a path the tool or payload writes (markers, output files, sink folders), `ResolveTestArtifactDir()` for the folder, `FindWorkspaceRoot()` for the `ysonet.sln` folder. The last chain entry is a `temp` at the system-drive root, derived from `SystemRoot`, not a hardcoded `C:`. The whole suite routes through them, so no test calls `Path.GetTempPath()` any more; `MakeTempFile` forwards to `WriteTestArtifact` and `MarkerPath` builds on `TestArtifactPath`. - They were documented in the 2026-07-21 rule below and in the consistency-check reference but had never been implemented, so the rule could not be followed.
- 2026-07-25 - Each run starts with `SweepStaleTestArtifacts()`, which deletes `ysonet_*` files/folders older than one hour from every candidate directory (skipping `ysonet_payloads*`, the wizard's default output name). - A fire marker is written by a spawned `cmd`, which can re-create it just after the test deleted it, so leftovers accumulated; the one-hour age rule means a second suite running at the same time never loses its live files. Housekeeping only - every fire helper still deletes its own marker before firing, so no result depends on the sweep.

- 2026-07-21 - New tests that write any file (fixture, input, payload, or a dropped marker) must write to the first writable directory in this order: workspace-root `temp` (gitignored) -> `Path.GetTempPath()` -> `C:\Windows\Temp` (via `%SystemRoot%`) -> `C:\temp`, verifying the file still exists after writing and falling through if it vanished. Use the `WriteTestArtifact` / `ResolveTestArtifactDir` / `FindWorkspaceRoot` helpers; never hardcode a machine path. - Antivirus sometimes deletes a generated payload or dropped marker as a false positive right after it is written, causing flaky failures; an AV-excluded workspace-root `temp` is the most reliable spot. Never loosen a behavioral assertion to dodge AV (test-integrity policy).
- 2026-07-24 - In `PayloadsFireIntoTestSinks`, `RunSTA` catches and discards every exception on purpose (most gadgets throw AFTER firing), so a harness bug inside the deserialize delegate is reported as the generic "marker not created" and looks exactly like a payload that did not fire. The concrete trap: the `deserAs` branches cast `r.Raw`, and NetDataContractSerializer output comes back BOTH ways - the identity-family gadgets hand-build an XML string, while gadgets that go through the base `GenericGenerator.Serialize` (TypeConfuseDelegate) return UTF-8 XML `byte[]`. Fixed by normalizing once in `DeserializeAs`/`Text`/`Bytes` instead of casting per branch; an unknown deserializer tag now throws instead of silently doing nothing. - When a fire row fails with "marker not created", suspect the harness (payload shape, wrong tag) before concluding the gadget does not fire.
- 2026-07-22 - Antivirus can intercept `csc.exe` and make the compile-based gadget tests (the ones that compile a `.cs`: `DataSetOldBehaviourFromFile`, `ActivitySurrogateSelectorFromFile`, `XamlAssemblyLoadFromFile`, `EveryGadgetGeneratesAPayload`, and the `*FromFile` fire tests) hang with low CPU, so the run never reaches the later tests. Pause AV or exclude the build output dir; killing `csc` does not unblock a wedged compile. - Real-time AV scanning of the temp-compiled assembly deadlocks the legacy CodeDom (`CSharpCodeProvider`) compile.
- 2026-07-26 - A per-process FRAMEWORK-BEHAVIOUR switch is testable without touching the machine: compile a child exe at test time and stamp it with `[assembly: TargetFramework("...")]`. `ysonet.Tests/LegacyXmlChild.cs` does this for `DataViewManagerXxe`, whose effect needs the pre-4.5.2 XML resolver default. The chain is `XmlReaderSettings.EnableLegacyXmlSettings()` -> true when `!BinaryCompatibility.TargetsAtLeast_Desktop_V4_5_2` -> `BinaryCompatibility.ReadTargetFrameworkId()` -> `AppDomain.CurrentDomain.GetTargetFrameworkName()`, i.e. the ENTRY assembly's attribute. Two consequences: a new AppDomain cannot help (the `BinaryCompatibility` static lives in mscorlib, which is domain-neutral, and a 200-test run has long since cached it), and NO targeting pack is needed because the attribute is only a string the CLR reads back - compile against whatever reference assemblies the machine has. That is what keeps the test runnable for a dev without the 4.5.1 dev pack, and it avoids the documented alternative of writing `EnableLegacyXmlSettings` to HKLM/HKCU, which would change the whole machine. Keep the listener in the PARENT and put only the deserialize in the child, have the child PRINT the switch it resolved (the row asserts `legacyXml=True`, so a silent flip fails loudly instead of passing vacuously), and always pair the legacy rows with a hardened-moniker control that must NOT fire. 12 cells: 5 formatters x minify, plus 2 controls. - Without the printed-state assertion the whole matrix would still pass if the child quietly stopped being legacy, which is the failure mode that matters.
