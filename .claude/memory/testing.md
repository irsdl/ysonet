# Testing (ysonet.Tests)

- 2026-07-29 - A NEW MODULE MUST BE EXERCISED THROUGH EVERY SURFACE THAT CAN BUILD IT, NOT JUST THE CLI, and asserting that a UI field EXISTS is not asserting what it CONTAINS. `DataTableTypeSpoof` passed a full green FULL run - generation matrix, ten fire rows, exact-bytes guards - while the interactive editor emitted a truncated `--target-type` and produced a payload that never fired, because every one of those checks drives `PayloadRunner` directly and the editor's defaults are recovered from the option HELP TEXT, a path no CLI test touches. Its one editor test asserted the assembly help was not turned into a choice MENU and that `bgc` was hidden, both true, both beside the point. Three guards now cover the class, and they are the shape to copy for any surface that can build a payload. (1) `EveryGadgetEditorDefaultMatchesTheGadgetsOwnDefault` - for every gadget, generating with the editor's own emitted argv (`GadgetExtraArgvForTest`) must be byte-identical to generating with no options; that IS the definition of a default, and it fails loudly on any module. It generates the plain payload TWICE first, so the three `*FromFile` gadgets that compile an assembly are detected as non-reproducible and reported BY NAME rather than silently dropped. (2) `EditorDefaultsAreCompleteValuesNotTruncations` - a cheap parser-independent invariant over every gadget AND plugin option: the character after the recovered default in the help must end a value. (3) `ParseDefaultKeepsDottedValuesWhole` pins the helper's rule directly. - Prove causality before believing a guard: reverting both fixes turns all four checks red with the exact wrong value named, and restoring them turns them green.

- 2026-07-29 - THE EDITOR IS BUILT PER MODULE KIND AND THE WRONG KIND COVERS NOTHING SILENTLY. `new ModuleEditor(keys, out, isGadget, ...)` - passing `true` for a PLUGIN name makes `ModuleView.FromGadget` fail, `LoadModule` return false, and `BuildFieldsForTest` hand back an empty field list: no exception, no failure, and an audit that reports success having examined zero plugins. The first version of the default audit above did exactly this and its "3 checked" was the only visible symptom. Carry the kind with the name (a `KeyValuePair<string,bool>` list), assert a non-empty field list per module, and count the two halves SEPARATELY so a half that stops covering anything fails instead of passing quietly. - Same family as the environment-verdict rule: a check that silently examines nothing reads exactly like a check that passed.

- 2026-07-29 - A WIRE-NAME ASSERTION ON A SOAP PAYLOAD NEEDS ONE FORM PER MINIFY STATE, which is a third trap beside the two already recorded here (LosFormatter base64, SOAP splitting a type name into an element plus an `nsassem` namespace). Raw SOAP percent-encodes the assembly identity inside that namespace URI (`System.Data.Entity.Design%2C%20Version%3D4.0.0.0%2C...`), and the XML minifier writes the DECODED form with the space after each comma collapsed (`System.Data.Entity.Design,Version=4.0.0.0,...`). Both name the same assembly and both bind, so the check is per state; a single loose substring that passes on both would stop proving the identity is complete. The element PREFIX also changes with minification (`a1:` becomes `f:`), so match `:TypeName`, never `a1:TypeName`. - `DataTableTypeSpoofNamesTheSubclassOnTheWire` failed on exactly one of its six cells the first time, and the failure looked like a lost assembly name rather than a re-encoding.

- 2026-07-29 - AN `OutputPath` OVERRIDE MUST SIT ABOVE THE `Microsoft.CSharp.targets` IMPORT, AND `ysonet.Tests.csproj` HAD IT BELOW. `OutDir` is derived from `OutputPath` inside that import, at EVALUATION time, so the private-build override placed after it changed nothing and a `-p:IncludePrivateModules=true` build quietly wrote `ysonet.Tests.exe` into the PUBLIC checkout's `bin\Debug` - the one thing the two build modes exist to prevent. It produced no error and no visible symptom because the sibling `YsonetOutDir` override in the same block DID take effect (a plain property read inside a target is resolved when the target runs), so the staged copy landed in the private root and the run looked correct. `ysonet.csproj` was always right, purely because its import is at the bottom of the file. The fix splits the block: `OutputPath` above the import, `YsonetOutDir` left below it (it has to stay after the unconditional default a few lines up, which would otherwise overwrite it). - Two properties in one PropertyGroup behaved differently for a reason nothing in the file hinted at, and the failure mode was a private binary appearing in the public tree with a green build.

- 2026-07-29 - RUNNING THE SUITE FROM A RELOCATED OUTPUT NEEDS `YSONET_REPO_ROOT` IN THE RUN ENVIRONMENT, not just in the build. `FindWorkspaceRoot()` and the completion-script reader walk UP from the test binary, which no longer reaches the repo when the output has been moved, and they fall back to that variable. - 2026-07-29 - NOTHING USED TO ASSERT THAT `-t` PRODUCES AN EFFECT, which is why a self-test question took a day to answer. Every fire test generates with `Test = false` and deserializes through the harness's own helper, so they prove the PAYLOAD works and say nothing about the product's self-test path - a different deserializer call, on a different thread, with its exception swallowed. `SelfTestFiresThroughTheProductsOwnPath` closes that: generate with `Test = true`, let `FireBackend` own the marker, and assert it fires for every advertised formatter. It passes for all six on `WindowsIdentity`, which settles the open LosFormatter question (`-t` was never broken there; `GenericGenerator.Serialize` was not changed) and it also FAILS without the `<root>`-envelope fix in that gadget's NDCS `Test` branch, so that fix is proven end to end rather than by inspection. Pair it with the `ShowErrors` change below: a `-t` that fires is now assertable, and a `-t` that does not now says why. - "The payload works" and "`-t` works" are different claims, and only the first had coverage.

- 2026-07-29 - `Debugging.ShowErrors` NOW EXPLAINS ITSELF, and it moved to STDERR. It used to print `err.StackTrace` and nothing else - no exception type, no message, no `InnerException` - so "died inside the deserializer" and "reached the sink and fired" produced identical output, and every formatter-shape failure (which names its cause in the INNER exception: "Invalid cast from System.String to System.Byte[]", "Member 'X' was not found") was invisible. It now walks the chain printing type and message, then the outermost trace. The stream change is not cosmetic: stdout carries the payload, so `--debugmode -o raw > payload.bin` was already writing a stack trace into the payload file, and lengthening the output would have made that worse - `ShowNote` always followed that rule and the comment excusing `ShowErrors` ("nobody pipes a debug run") is gone. Locked by `ShowErrorsExplainsTheWholeExceptionChain`, which also asserts stdout stays empty and that a quiet run, a null exception and null args are all silent (every call site is inside a catch block). - One missing `err.Message` is the difference between a five-minute diagnosis and an inconclusive day.

- 2026-07-29 - DRIVING `ysonet.exe -t` FROM A SHELL IS NOT A FIRE AUDIT, and this is the run that proves it rather than repeating the warning: 36 cells probed by generating with a marker command and checking for the file gave 25 hits, then 0 hits for the same cells on a repeat, then 0 for cells that had hit twice - while the identical 36 cells run through the harness (`FireBackend` + `PayloadRunner.GenerateGadget` + `RunSTA` + `DeserializeAs`) fired 36/36. The reason nothing can be diagnosed from the CLI is `Debugging.ShowErrors`: it prints `err.StackTrace` ONLY - no exception type, no message, no `InnerException` - so a self-test that died in the deserializer looks exactly like one that fired. Use the harness for any "does this cell fire" question; a temporary `Run(...)` at the top of `Main` costs one 58-second NORMAL run and there is no per-test filter. Two things were found underneath the noise. `NetDataContractSerializer_deserialize(str)` (the one-argument overload) feeds the WHOLE document to NDCS, which cannot read the `<root>` envelope that `WindowsIdentity` and `WindowsClaimsIdentity` alone wrap their NDCS payload in - `WindowsIdentity`'s `-t` had always thrown there and reported nothing, and the harness needed a new `ndcroot` tag in `DeserializeAs` for the same reason. And a bridged inner payload is a base64 STRING member, so asserting "the bridged graph is in there" needs the longest base64 run decoded first (`DecodedInnerBlob`), never a literal substring search on the outer bytes. - A whole day can go into a payload that was never broken, and the swallowed message is what makes that possible.

- 2026-07-28 - A GADGET WHOSE TARGET CREATES A WPF `System.Windows.Application` MUST BE FIRED IN A CHILD PROCESS, and the reason is not safety but arithmetic: that object is a per-AppDomain SINGLETON with thread affinity, so in-process the first cell would leave a live Application inside the test runner for every later test to inherit, and the second cell - on the next `RunSTA` thread - would fail reaching `Application.Current` from the wrong thread. Both outcomes are the harness inventing a result. `FireWorkflowDesignerSubprocess` spawns `ysonet.exe -g <gadget> -f <fmt> -c <sink> --rawcmd -t` per cell (16 cells: 8 formatters x minify) and asserts the sink, which also exercises the product's own `SelfTestNeedsStaThread` wiring rather than a bare deserialize the harness arranged. Same shape as `FireSelfClosingCs` and `FireResxCompiledSubprocess`; drain both pipes asynchronously as they do. - The in-process default is right for almost every gadget, and the one thing that makes it wrong here is invisible until cell 2 fails with a threading error that looks like a payload bug.

- 2026-07-28 - THE HARNESS FOR A DENIAL-OF-SERVICE GADGET DRIVES THE PRODUCT, NOT A REHOSTED COPY OF IT. `dev-kitchen/tools/wsman-dos-harness.ps1` runs `ysonet.exe -g <gadget> -f <formatter> --i-understand-dos -t` per formatter x minify and requires the child to die with the TARGET'S OWN exception text (`Handle is not initialized.`), which is simultaneously proof that the formatter constructed the target and proof that the effect fired; anything else that dies is reported SUSPECT rather than passing. 26/26 stable. (1) DO NOT HOST ysonet.exe INSIDE POWERSHELL to call its helpers directly: PowerShell resolves assemblies against ITS app base, and the `AssemblyResolve` handler needed to work around that re-enters through the cmdlets it calls, so the child dies of a `StackOverflowException` (0xC00000FD) that reads exactly like a payload crash - and intermittently, because it depends which assemblies need resolving. (2) DO NOT ADD A SEPARATE "did it construct the target?" PROBE: it must keep the object alive to report its type, and an allocation-heavy deserializer (MessagePack Typeless, Lz4 worst) collects an unreachable instance MID-READ so the probe dies before it can log; a `TryStartNoGCRegion` around the read did not fix it. The exception text already carries the construction evidence, so the probe was redundant as well as flaky. - A harness that is less trustworthy than the thing it measures is worse than no harness, and both dead ends fail in the direction of blaming the gadget.

- 2026-07-28 - THE ISOLATED SELF-TEST IS NOW THE ONLY WAY A DENIAL-OF-SERVICE GADGET CAN BE `-t`-ED, and making it work needed three changes, each of which was a silent failure before. (1) THE FORMAT MAP IS SHARED. `IsolatedSelfTest.Deserialize` knew only BF/Los/Soap/NDCS, so a DoS gadget on a hand written format could not be self-tested at all; the map moved to `Helpers/Serialization/PayloadReader` and BOTH the in-process path (`GenericGenerator.DeserializeHandWritten`) and the child call it, so "the child tests what the in-process path would have tested" is true by construction. `PayloadReader.CanRead` plus `PayloadReaderCoversEveryAdvertisedFormatter` walk every registered gadget's `SupportedFormatters()`, so a future gadget advertising an unreadable format fails at build time instead of when someone types `-t`. Watch the BYTES/TEXT split: the child only ever gets bytes (the parent writes a file), so handing a BinaryFormatter stream to a text reader looks exactly like a payload that does not work. (2) THE CHILD MUST FORCE A COLLECTION. The effect is on the FINALIZER, so without `GC.Collect`/`WaitForPendingFinalizers`/`GC.Collect` after the read the child exits 0 and a working payload is reported as doing nothing; it runs even when the read THREW, because a deserializer that builds the target and then fails has still armed it. (3) REPORT THREE OUTCOMES, NOT TWO. Exit 0 = survived, exit 1 + stderr = the DESERIALIZER refused it, anything else = the payload fired and killed the child - for a payload whose point is to kill its host, "the reader would not build it" and "it built it and died" are indistinguishable from an exit code alone. Also: walk to the INNERMOST exception when reporting (FsPickler's outer message is the useless "Error deserializing object of type 'System.Object'"), and `YSONET_SELFTEST_ROOTTYPE` carries the DataContractJsonSerializer root type as a NAME the child resolves, so the generator never loads a target assembly. The observed kill is `0xE0434352` plus `System.InvalidOperationException: Handle is not initialized.` - the CLR's managed-exception code, NOT the `0xC0000409` fail-fast the XAML wrapper produces, so do not make one exit code the contract. - Every one of the three would have shown up as a green run that proved nothing.

- 2026-07-28 - NO TEST MAY DESERIALIZE A DENIAL-OF-SERVICE PAYLOAD, SO ITS EFFECT EVIDENCE IS THE PRODUCT'S OWN `-t`, run by hand and recorded. `WSManPluginInstance` was audited with `ysonet.exe -g WSManPluginInstance -f <formatter> --i-understand-dos -t` across 13 formatters x minify; each row's pass condition is the child dying with the target's own exception. - 2026-07-27 - AN ACCEPT-AND-CLOSE LISTENER CANNOT PROVE TWO THINGS a callback row often needs: WHICH url was requested, and what happens NEXT. `LegacyXmlHttpServer` (a plain `TcpListener` on `127.0.0.1:0`, so the same `loopback-tcp` capability the shared probe measures) answers and RECORDS: routes registered up front, every request target kept in arrival order, and an unregistered path answered 404 and still recorded, because "the target asked for the wrong thing" beats a timeout. (2) A `WaitForRequest(prefix, ms)` that RETURNS THE TARGET, not a bool, is what lets the row assert the query string a disclosure chain put in it. - 2026-07-27 - THE HIDDEN DESKTOP CANNOT CONTAIN A CONSOLE WINDOW ON WINDOWS 11, and that is why pop-ups survived the quiet-run work. Windows 11 does not host a new console itself: conhost hands hosting to the user's DEFAULT TERMINAL APPLICATION over COM, and that terminal is an already-running process of the user's own, not a descendant, so it never inherited `STARTUPINFO.lpDesktop` and its window opens on the visible desktop. Measured on build 26200 with an EnumWindows watcher over the interactive desktop: `Process.Start(file, args)` (UseShellExecute defaults to TRUE, and ShellExecuteEx creates a NEW console for a console program - the opposite of `SEE_MASK_NO_CONSOLE`) pops a `CASCADIA_HOSTING_WINDOW_CLASS` window hosted by the running `WindowsTerminal.exe`, with `OpenConsole.exe -Embedding` parented by `svchost.exe` as the COM fingerprint; `UseShellExecute=false` with or without `CreateNoWindow`, and `UseShellExecute=true` with `WindowStyle=Hidden`, are all clean. So it is the PAYLOAD's own spawn that escapes, never the runner's. In practice only the product's non-raw `-c` wrapper reaches it, because that runs `cmd /c <sink> <tag>` and cmd is a console program; a raw command runs the windowless `ysonet.TestSink.exe`, which allocates no console and shows nothing. Nothing in the process can scope the decision (conhost reads it per USER at console-creation time), so `UiIsolation.ClassifyConsoleHandoff` reports it as one header note and the runner NEVER writes the setting. - The old comment claimed the desktop was inherited "the whole way down", which was true on Windows 10 and is no longer the whole story; believing it sends you hunting for a runner bug that does not exist.
- 2026-07-27 - A FIXED FIXTURE NAME IS A RACE, so every helper-managed artifact now lives in a PER-RUN namespace: `ResolveTestArtifactDir()` returns `<root>\ysonet_run_<pid>_<8 hex>` and `WriteTestArtifact` walks the run directory under each root, not the roots themselves (that second half is the easy miss - changing only the resolver leaves every `WriteTestArtifact` fixture in the shared root). The four ROOTS and their order are unchanged. Add nothing per call site: the namespace belongs to the shared helpers so future fixed names are safe for free. - Two concurrent runs (trivial to hit: a Debug build runs the NORMAL suite as a post-build step, so it overlaps a manual `--full`) clobbered `ysonet_wbem_prepared.bin` and `ysonet_fileops_minify_probe.txt`, and both failures read like a gadget or minifier bug rather than the file race they were.
- 2026-07-27 - THE STALE SWEEP NEEDS OWNER LIVENESS, NOT JUST AGE, once artifacts live in per-run directories: a FULL run passes the one-hour cutoff while it is still working, and with `--status-file=off` there is no other evidence it exists. `SweepStaleArtifacts` keeps any entry whose NAME ends with a run token `<pid>_<random>` while that pid is alive (`RunStatus.ProcessIsAlive`, injectable in the focused test), and applies the age rule to everything else. The build folder is swept with the narrow `LegacyXmlChild.ArtifactPattern`, never with the broad `ysonet_*`, because it holds the product output. A run also deletes its own directory at the end when no file was left anywhere below it. - Without the liveness rule, a per-run directory is worse than the old flat layout: one sweep could delete a live FULL run's whole working set.
- 2026-07-27 - AN ENVIRONMENT SKIP IS ONLY HONEST WHEN THE PREREQUISITE IS PROBED SEPARATELY FROM THE PAYLOAD, and four facts made that harder than it looks. (1) REGISTRATION IS NOT DNS. `OobSession.TryStart` proves the interactsh client registered a payload domain, which is an HTTPS exchange with the API; it does NOT prove a DNS query for a name under that domain reaches the authoritative server. They are two capabilities (`oob-endpoint`, `oob-dns`), and the second is the one the payload rows actually depend on. The old README claimed registration failure covered a resolver that blocks OAST domains, and that was simply false. (2) MATCH THE PROTOCOL EXACTLY. `Observed(label)` accepted ANY protocol, but interactsh answers a TLS request as `https` and a plain one as `http`, and the pinned client emits more protocols than the three the docs listed, so "any" silently widens over time and lets one signal stand in for another. Every assertion now waits for the exact protocol name. (3) SMB CARRIES NO `full-id`. interactsh v1.3.1's SMB server writes protocol `smb` with no label, so `ProtocolsFor(label)` can NEVER find it - the only correlation left is positional: count complete JSONL records before the action (`CaptureInteractionCursor`), then look only after that point, run UNC actions serially, and finish each wait before the next. Anyone who "fixes" this by looking for a labelled smb record is chasing something that does not exist. (4) AN ABSENCE CONTROL SHARES ITS POSITIVE ROW'S PREREQUISITE. The hardened `DataViewManagerXxe` cells and the OOB controls assert that NOTHING arrives, so on a blocked loopback stack or a blind endpoint they pass while proving nothing; they are gated on the same capability as the positive cells. - Each one turns a green tick into a lie in a different way, and none of them shows up as a failing test.
- 2026-07-27 - EVERY AUTOMATED UNC TOUCH NEEDS A SELF-HOSTED SERVER, and `YSONET_INTERACTSH_SERVER` is the operator's DECLARATION that they own it - the harness cannot prove ownership. Windows sends authentication material when it opens an SMB session, so on the default public endpoint the credential-safety boundary would be a third party's SMB configuration, which can change. `RunOwnedUnc` in `Tests.cs` is the single choke point and refuses unless the capability is Present; the two UNC checks are then named skips and the SMB diagnostic is `NOT-PROBED`, decided BEFORE any label, path, or socket exists (the focused test passes a null session to prove the gate decides first). Constructing or serializing a UNC string is inert and is not a touch. This gates the TEST HARNESS only: a user running `ysonet.exe -t` is unchanged and stays governed by the gadget they chose. - The earlier tests touched UNC paths on the public endpoint, which made credential safety depend on a third party continuing not to answer SMB.
- 2026-07-27 - FAILURE COUNTS MUST BE RECORDED, NEVER DERIVED. `Run` increments `_passed`/`_failed` once per TOP-LEVEL test while `PayloadsFireIntoTestSinks` collects many cell failures and throws ONE aggregate exception, so "ordinary failures = `_failed` minus capability failures" is arithmetic on two different units and is always wrong. `FailureCollector` replaced that matrix's `List<string>`: `Add` is ordinary, `AddCapability` is capability-dependent, and `Run` opens a scope so a test that throws with no cell records is counted once and one that already reported its cells is not counted twice. Classify by the ASSERTION that failed, not the helper it lives in - a generation failure, a wrong payload type, a missing sink frame, or an absence control that saw forbidden activity stays ordinary whatever the network did. The verdict token is environment CONFIDENCE, not success, which is why `clean` can coexist with an ordinary failure that still exits 1. `--strict-env` changes only the EXIT requirement and never runs a row whose prerequisite is absent. - The first draft derived one counter from another and could report `mixed` on a run with no environmental problem at all.
- 2026-07-27 - DO NOT INSTALL AN ACCEPT-ALL CERTIFICATE CALLBACK TO MAKE AN HTTPS PROBE SUCCEED. It has to go on `ServicePointManager.ServerCertificateValidationCallback`, a process global every later request in the run inherits, so one diagnostic would silently disable TLS trust for the whole suite. Measured on 2026-07-27 against the public OAST endpoint: the `https` egress signal comes back `NOT-CONCLUSIVE` with "Could not establish trust relationship for the SSL/TLS secure channel" while `http` is `OBSERVED`. That is the correct outcome - the signal is diagnostic and never gates a row, and the evidence names the real reason. A focused test locks both `ServerCertificateValidationCallback` and `SecurityProtocol` by driving the whole request path against a loopback socket that accepts and closes, so the TLS-failure branch runs with no packet leaving the box. - "Make the probe green" and "keep TLS trust intact for 280 other tests" point in opposite directions, and only one of them is worth having.

- 2026-07-27 - AN AUTOMATED RUN NOW HIDES ITSELF AND REPORTS ITSELF, and four separate mechanisms do it, each with an off switch (`--ui-isolation=none`, `--wer-containment=off`, `--status-file=off`, `YSONET_TEST_SINK=off`). Facts worth keeping, because each one was learned the hard way: (1) A CONSOLE FLAG CANNOT WORK for this. The runner starts ysonet.exe children with `CreateNoWindow`, which gives a console app NO console, so the payload GRANDCHILD that actually flashes has no runner console to inherit - only a hidden DESKTOP is inherited the whole way down (`STARTUPINFO.lpDesktop`). (2) `CloseDesktop` FAILS while a thread of the calling process still uses the handle, so `CreateDesktopW` and `CreateProcessW` run on a short-lived dedicated thread that exits before the parent waits and closes; and both pipes must be drained CONCURRENTLY or a child filling one deadlocks the parent. (3) One job with `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION` covers the whole tree (it applies `SEM_NOGPFAULTERRORBOX` to every member), which is why no `SetErrorMode` call was added to the product; `KILL_ON_JOB_CLOSE` is deliberately NOT set, so the job never redefines child lifetime or hides a hang. (4) There is NO `crashed` status state and there must not be: `AppDomain.UnhandledException` is not raised for every process-corrupting exception and nothing runs after a kill, so an interrupted run is `state=running` with a heartbeat that stopped. - The first draft assumed an `AllocConsole` mode and a `crashed` state, and both are unimplementable rather than merely awkward.
- 2026-07-27 - A STATUS FILE THAT PUBLISHES BY RENAME MUST RETRY, or an ordinary reader silently kills it. `RunStatus` writes a temp file and `File.Replace`s it into place so a reader never sees a partial snapshot - but `File.ReadAllText` opens with `FileShare.Read`, which DENIES the rename, so one `type statusfile.txt` at the wrong moment failed the publish. The first version disabled status permanently on the first failure (which is what the plan said) and a test with a polling reader caught it immediately: the file froze at `index=0`. Fix is a short backoff inside one publish (8 attempts, ~0.6s total) and disabling only when all of them fail; a directory that cannot be created is treated as permanent and does not retry. - "Disable on first I/O error" reads as safe but turns a maintainer glancing at the file into a silent loss of observability for the whole run.
- 2026-07-27 - DO NOT ASSERT `SEM_NOGPFAULTERRORBOX` IN A MANAGED CHILD to prove WER containment - assert the JOB LIMIT instead. `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION` is documented as forcing `SetErrorMode(SEM_NOGPFAULTERRORBOX)` on every member, so the obvious test is to spawn a child and read `GetErrorMode`. Measured on 2026-07-27: a managed child reported `errorMode=0x8001` (FAILCRITICALERRORS | NOALIGNMENTFAULTEXCEPT, no NOGPFAULTERRORBOX) while `IsProcessInJob` against the named job was true - the .NET Framework CLR sets the process error mode during startup, and a process may change its own error mode after joining a job. The same assertion PASSED on other runs of the same binary, so it is also flaky. `WerProbe` now reports `inJob` and `jobLimit` (the named job queried back for the flag) and the test asserts both; the error mode is printed as diagnostics only. The behavioural evidence is separate and cheap: after a FULL run containing the deliberate CLR fail-fast rows, `Get-Process WerFault` reports zero processes. - The per-process bit is an implementation detail the child can legally overwrite; the job limit is what Windows actually enforces.
- 2026-07-27 - A HANDLE-COUNT LEAK TEST MUST COLLECT FIRST. `UiIsolationReleasesNativeResources` showed +200 handles over 20 hidden-desktop launches and looked like a real leak; it was `Thread` and `Stream` objects waiting for finalization, each still holding a handle. `GC.Collect()` / `WaitForPendingFinalizers()` / `GC.Collect()` before both measurements drops it to nothing. - Without the collect the test either fails on healthy code or needs a bound so loose it would miss a real leak.
- 2026-07-27 - THE FIRE SINK'S TAG STARTS WITH A DIGIT ON PURPOSE, and that is a TypeConfuseDelegate constraint, not a naming style. `BuildConfusedContainer` hands the LARGER of its two strings to the spliced `Process.Start`'s FIRST parameter under `String.Compare` (culture-sensitive), so the sink executable path must sort ABOVE the tag or the payload calls `Process.Start(tag, exe)` and nothing fires. A digit sorts below any drive letter, so `0p<pid>_<n>_<rand>` is always the smaller element. `FireBackend.Select` checks the invariant once against `"9" + 63 z's`, the largest tag the alphabet can produce, which is why no per-row check can fail. Second constraint on the same command: `CommandArgSplitter.SplitCommand` cuts at the FIRST ASCII space, so a sink path with a space is converted with `GetShortPathNameW` and RE-CHECKED - Windows returns the LONG path when a volume has no 8.3 names, so trusting the return value would produce a command silently cut in half. - Both failures would look like a broken gadget, not like a broken test harness.

- 2026-07-27 - RULE: an outbound-callback gadget wants BOTH effect tiers, because they prove different halves and neither subsumes the other. (1) LOOPBACK, in the default FULL tier, when the protocol has a local responder on its well-known port: point the payload at `127.0.0.1` and assert the ERROR THE REMOTE END SENT BACK. For the DCOM/RPC callback `0x80070776 OR_INVALID_OXID` ("the object exporter specified was not found") is the answer the local RPCSS gave, so it proves a COMPLETED RPC ROUND TRIP - stronger than a name lookup - while `0x800706BA RPC_S_SERVER_UNAVAILABLE` means nothing answered and `0x8003001E STG_E_READFAULT` means the blob never got that far. Pair it with a stack-frame check (the chain must name the native sink, here `CoUnmarshalInterface`) so the row also proves WHICH code path ran: the frame identifies the formatter as having driven the ISerializable constructor, the HRESULT identifies the round trip, and either half alone is weak. This is what makes per-formatter coverage affordable - 14 cells with no packet leaving the machine. (2) OOB/DNS, opt-in, for the half loopback can never show: that a name the target has NEVER SEEN is resolved and a genuinely remote host is reached. `WbemDcomCallbackIsObservedOutOfBand` is the pattern; it needed its own test rather than a `UncCallbackRows` row, because that table is UNC-path shaped and this gadget's `-c` is a bare host (`oob.HostFor(label)`). Do not treat one tier as a substitute for the other: loopback alone never leaves the box, OOB alone proves only the lookup and is opt-in. - Before this, the FileSystemInfo plan assumed a callback gadget needs a "test-owned endpoint" it cannot have; for a protocol already served locally you get a stronger result for free, and the remote half is then one extra opt-in row.
- 2026-07-27 - A GENERATION-ONLY CONTROL is the cheap way to prove a tool does not touch the operator's input while building it.
