2026-08-18 - TWO THINGS MAKE A UNC GADGET LOOK DEAD WHEN IT IS WORKING, AND BOTH ARE OUTSIDE THE GADGET. Proving an outbound SMB callback by hand produced "no packets, returns instantly" twice, and neither cause was the payload. FIRST, a `\\host` argument passed through a POSIX shell layer on Windows does not arrive as written, and WHICH WAY it is wrong depends on how the argument was formed. A LITERAL argument has its doubled backslashes collapsed (so `\\host` arrives as `\host`, a relative local path, and four are needed to get two); a value expanded from a VARIABLE is passed through untouched (so four stay four, `\\\\host\share\x`, which is not a UNC path either). The no-path-conversion environment variable stops neither. Both mistakes look identical from outside: the payload prints, the run succeeds, and the target makes no network call. Worse, they are not uniformly fatal - `Assembly.LoadFrom` and the WPF URI parser NORMALISE the extra separators away and still call out, while `DirectoryInfo`, `Path.Combine` and `Directory.Exists` do not, so a sweep of seven gadgets came back with two "working" and five "broken" when the only difference was whose parser was forgiving. Read the emitted payload and count the backslashes before believing any negative result, and prefer PowerShell, which needs no escaping at all. SECOND, Windows CACHES a failed SMB target, so the second attempt at the same server returns in a fraction of a second and emits NO packet - a retry is indistinguishable from a gadget that never tried. Give each attempt its own address (extra addresses on the observer cost nothing) or wait the cache out, and always run the raw sink call as a control in the same window, because a control that produces the identical packet pattern is what turns "it fired" from inference into a comparison. - Both failures present as the gadget's fault, which is the one conclusion that leads to editing product code that was correct all along.

2026-08-18 - A TEST MODULE THAT OWNS ITS OWN FILE IS REGISTERED BY ONE CALL, AND NOTHING IN THE LANGUAGE MAKES THAT CALL MANDATORY. An uncalled `private static` method raises no compiler warning, so a dropped registration compiles clean, the suite stays GREEN, and the module's whole row set simply never executes - the exact outcome the test-integrity policy forbids, reached without anyone weakening a test. It has happened twice here: a merge that resolved a conflict in the shared registration point by taking one side (each side carried its own call and not the other's), and a module whose rows were only reachable from a focused debugging entry point. The guard is `EveryModuleTestRunnerIsRegistered`: it discovers every static `Run*Tests` method in the assembly BY SHAPE and walks the IL call graph from `Main`, failing with the orphan's name when one is never reached. Three things make it work rather than merely look like it works. It reads the COMPILED assembly, so it needs no path back to the checkout and runs from `bin\`. It walks IL opcode by opcode with the real operand sizes taken from the runtime's own `OpCodes` table, because an operand byte can hold the same value as a `call` opcode and a byte-pattern scan would invent callees that are not there; an unknown opcode STOPS the walk, since reporting fewer callees can only make the guard stricter. And it does NOT cross a focused entry point or the private hook those hang off, because a module only a debugging hatch reaches is precisely the defect - a plain reachability walk from `Main` would count it as registered. Discovering by shape is also what lets one PUBLIC guard cover a mounted private area: private modules are the same partial class in the same assembly, and the guard names none of them. Measured: orphaning one registration removed 13 rows from a 515-row run and produced exactly ONE failure, the guard's. - Coverage that depends on someone remembering a line is not coverage; the drop is invisible in every signal a green run produces.

2026-08-14 - A CAPABILITY GATE MUST MARK A TERMINAL STATE BEFORE ANYTHING QUERIES IT, OR IT FAILS OPEN AND LOOKS EXACTLY LIKE A PASSING TEST. 2026-08-10 - TWO TEST RUNS ON ONE MACHINE PRODUCE FAILURES THAT LOOK ORDINARY, AND ORDINARY IS THE ONE CLASSIFICATION THAT TELLS AN AGENT TO CHANGE PRODUCT CODE. Measured during a concurrent multi-agent run: two suites testing at the same time gave three failures and a silent fall back from the windowless fire sink to the legacy `cmd` marker, and both went green when re-run alone with no product change. Separate checkouts do not help - the per-run filename namespacing (per-run artifact directory, PID-suffixed status file, PID+counter sink tags, per-run legacy-child compile names) was ALREADY in place when this happened, because what actually collides is not a name: it is CPU, the shared local probes, and the tight launch-and-read budgets the sink probe and every fire row wait on. Three properties make it safe to take unconditionally: a killed holder ABANDONS the mutex, so a dead run can never wedge the machine (`AbandonedMutexException` means this thread now owns it); a lock that cannot be created prints one line and the run continues unserialised; and the waiting run names its holder from that holder's own status snapshot rather than a second file that could disagree with it. What the lock deliberately does NOT cover: two agents sharing ONE checkout, where the other one can rebuild `bin\Debug` or run payloads under a suite that is already running. No lock inside the runner can hold that still, and the answer is the existing one - give each agent its own worktree. - The instinct is to isolate the FILES and call concurrency handled; the resources that actually break a run have no names to namespace.
